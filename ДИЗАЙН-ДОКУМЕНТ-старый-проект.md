## 0. Что это за продукт (в двух абзацах)

Это **интернет-магазин внутри Telegram**. Покупатель открывает бота `@ChannelCheckerBot`, жмёт `/start`, получает кнопку «🛍️ Открыть магазин», которая открывает **Telegram Mini App** (веб-приложение внутри Telegram) с каталогом товаров. Покупатель собирает корзину, оформляет заказ (ФИО, телефон, адрес Новой Почты, промокод, комментарий) — заказ улетает на бэкенд.

Админ управляет магазином двумя способами: (1) через **веб-админку** (`/admin.html`, вход по паролю) — товары, теги, промокоды, заказы, шаблон оплаты; (2) прямо **в Telegram** — каждый заказ создаёт отдельную тему (forum topic) в админ-группе, где админ жмёт инлайн-кнопки (Одобрить / Отклонить / Выслал / Доставлено / Отправить счёт) и **переписывается с покупателем через бота** (бот пересылает сообщения в обе стороны).

**Стек:** Java 21, Spring Boot 4.0.1, MySQL 8.4, Telegram long-polling bot, фронтенд — голый HTML/CSS/JS без фреймворков. Деплой — Docker.

### 1.3 Деплой
**Прод** (`docker-compose.yml`, 3 сервиса):
```
Telegram ──HTTPS──> Caddy (:443→host :8443) ──> app:8080 ──> MySQL db:3306
```
- `db` — MySQL 8.4, том `tgshop_mysql`, healthcheck.
- `app` — образ из Docker Hub (`${DOCKERHUB_USERNAME}/tg-shop-miniapp:latest`), собирается в CI.
- `proxy` — Caddy 2.8, TLS через **вручную выданные** сертификаты (certbot DNS-challenge), HTTPS на **нестандартном порту 8443** (он попадает в `WEBAPP_BASE_URL`).

**Локально** (`docker-compose.local.yml`, 2 сервиса, без Caddy):
```
Telegram ──> ngrok (HTTPS) ──> localhost:8080 (app) ──> MySQL db:3306
```
- `db` авто-заливается из дампа (`safety-backups/...sql`, ~136 МБ, схема + данные + 1196 картинок) **только при первом старте** (пока том пустой).
- `app` собирается локально из `Dockerfile`. **Flyway выключен** (`SPRING_FLYWAY_ENABLED=false`), т.к. дамп без таблицы истории Flyway; схему добивает `ddl-auto=update`.
- HTTPS наружу даёт ngrok.

**CI/CD** — GitHub Actions (`.github/workflows/docker-publish.yml`): на push в любую ветку и теги `v*` собирает мультиарх-образ (`amd64,arm64`), пушит в Docker Hub.

## 2. Модель данных (схема БД)

Деньги везде — **целые «минорные единицы»** (`*_minor`, копейки), валюта отдельным полем (дефолт `UAH`). Главные сущности используют **`BINARY(16)` UUID** (генерируется приложением в `@PrePersist`). Дочерние таблицы — `BIGINT AUTO_INCREMENT`.

### 2.1 `products` (Product)
| поле | тип | примечание |
|---|---|---|
| id | BINARY(16) | PK |
| title | VARCHAR(255) | NOT NULL |
| description | TEXT | nullable |
| price_minor | BIGINT | NOT NULL |
| currency | VARCHAR(8) | дефолт `UAH` |
| stock | INT | для товаров с вариантами — **производное** = сумма стоков вариантов |
| active | BOOLEAN | показывать в каталоге |
| archived | BOOLEAN | мягкое удаление (V2) |
| created_at | TIMESTAMP | |

Связи: `images` (1→N, OrderBy sortOrder), `variants` (1→N), `tags` (M↔N через `product_tags`).

### 2.2 `product_images` (ProductImage)
`id BIGINT PK`, `product_id` (FK CASCADE), `url VARCHAR(2048)`, `sort_order INT`. **url — это строка-ссылка** (обычно `/media/...`), не бинарь.

### 2.3 `product_variants` (ProductVariant) — V4, stock в V5
`id BINARY(16) PK`, `product_id` (FK CASCADE), `name VARCHAR(128)`, `stock INT` (V5), `sort_order INT`.
**Правило:** если у товара есть варианты — в заказе вариант **обязателен**; если вариантов нет — указывать вариант нельзя.

### 2.4 `tags` (Tag) — V3
`id BINARY(16) PK`, `name VARCHAR(128) UNIQUE`, `created_at`. Join-таблица `product_tags(product_id, tag_id)`.

### 2.5 `orders` (OrderEntity)
| поле | тип | примечание |
|---|---|---|
| id | BINARY(16) | PK |
| subtotal_minor | BIGINT | сумма до скидки (V4) |
| discount_minor | BIGINT | скидка (V4) |
| total_minor | BIGINT | итог = max(0, subtotal − discount) |
| promo_code | VARCHAR(64) | снимок кода (V4) |
| currency | VARCHAR(8) | **хардкод `UAH`** при создании |
| customer_name, phone, address | | NOT NULL |
| comment | VARCHAR(1024) | nullable |
| tg_user_id | BIGINT | Telegram id покупателя |
| tg_username | VARCHAR(255) | nullable |
| status | VARCHAR(32) | строковый «энам», дефолт `NEW` |
| tracking_number | VARCHAR(128) | ТТН (V2) |
| admin_chat_id / admin_thread_id / admin_thread_message_id | | тема заказа в Telegram (**нет миграции, создаёт Hibernate**) |
| admin_board_chat_id / admin_board_thread_id / admin_board_message_id | | карточка на «доске» (V7) |
| created_at | TIMESTAMP | |

Связь: `items` (1→N, CASCADE).

**Статусы заказа (строки):** `NEW → APPROVED → SHIPPED → DELIVERED`, плюс `REJECTED` (из любого). Сравнения регистронезависимы.

### 2.6 `order_items` (OrderItem)
`id BIGINT PK`, `order_id` (FK CASCADE), `product_id BINARY(16)` (**сырая ссылка, без FK**), `title_snapshot`, `price_minor_snapshot`, `variant_id` (V4, nullable), `variant_name_snapshot` (V4), `quantity INT`.
**Снимки** (title/price/variant) замораживаются на момент заказа — история не меняется при редактировании товара.

### 2.7 `order_messages` (OrderMessageEntity) — V8
Лог переписки по заказу: `direction` (USER/ADMIN/SYSTEM), `sender_name/id`, `message_type` (TEXT/PHOTO/DOCUMENT/...), `text VARCHAR(8192)`, `file_id`, `file_name`, `mime_type`, `tg_message_id`, `tg_reply_to_message_id`, `created_at`.

### 2.8 `promo_codes` (PromoCode) — V4, fixed-amount в V6
`id BINARY(16) PK`, `code VARCHAR(64) UNIQUE`, `discount_percent INT`, `discount_amount_minor BIGINT` (V6), `max_uses INT` (null = безлимит), `uses_count INT`, `active BOOLEAN`, `created_at`.
**Логика скидки:** фикс-сумма приоритетнее процента. Если `discount_amount_minor > 0` → скидка = `min(subtotal, amount)`; иначе если `percent > 0` → `(subtotal * percent) / 100` (целочисленно). При применении `uses_count++`.

### 2.9 `settings` (Setting)
Просто key/value: `k VARCHAR(128) PK`, `v VARCHAR(2048)`. Используется для: `PAYMENT_TEMPLATE_HTML` (шаблон оплаты), `ADMIN_CHAT_ID`, `ADMIN_ORDER_BOARD_NEW/PROCESSING/SHIPPED/CLOSED` (привязка стадий доски к темам).

### 2.10 `media_images` (MediaImage) — **нет миграции, создаёт Hibernate**
Картинки хранятся **бинарём в БД** (не на диске!): `id BIGINT PK`, `product_id BINARY(16)`, `filename VARCHAR(255) UNIQUE`, `content_type`, `data LONGBLOB`.
Поток картинок: внешний URL → скачивается → байты в `media_images` → публичный URL `/media/{filename}` → эта строка пишется в `product_images.url` → отдаётся обратно `MediaController`-ом из БД.

### 2.11 История миграций
V1 (база) → V2 (archived + tracking, **дубликат версии!**) → V3 (теги) → V4 (варианты + промокоды) → V5 (сток вариантов) → V6 (фикс-сумма промо) → V7 (колонки доски) → V8 (order_messages).

## 3. REST API

База `/api`. Аутентификация двумя путями:
- **Telegram initData** — подписанная Telegram строка; бэкенд проверяет HMAC-SHA256 (ключ = `HMAC(botToken, "WebAppData")`). Флаг `ALLOW_UNSIGNED_INIT_DATA=true` полностью отключает проверку (только для дева). **Срок годности `auth_date` НЕ проверяется.**
- **Админ** — заголовок `X-Admin-Password` ИЛИ валидный initData с userId из списка админов.

### 3.1 Публичные / покупательские эндпоинты
| метод | путь | что делает |
|---|---|---|
| GET | `/api/products` | активные не-архивные товары + соль (soldCount) |
| GET | `/api/tags` | все теги |
| GET | `/api/app-info` | `{botUsername, webappBaseUrl}` |
| GET | `/api/me?initData=` | профиль вызывающего + флаг admin |
| POST | `/api/orders` | **создание заказа** (initData в теле) → `{orderId}`, 201 |

### 3.2 Логика создания заказа (`OrderService.createOrder`, транзакция) — ключевое
1. **Проверка наличия** (по всем позициям, накопительно для дублей строк): товар существует и `active`; вариант обязателен/запрещён по правилу; `stock >= суммарное qty`.
2. **Промокод** (`resolvePromo`): существует (регистронезависимо), `active`, не превышен `max_uses`.
3. **Шапка заказа**: данные клиента, `currency = "UAH"` (хардкод).
4. **Позиции + subtotal + списание стока**: создаются `OrderItem` со снимками; `subtotal += price_minor * qty`; сток вычитается (для вариантов — вычитается вариант, затем `product.stock` пересчитывается = сумма вариантов).
5. **Скидка**: фикс приоритетнее процента; `total = max(0, subtotal − discount)`; `promo.uses_count++`.
6. **Сохранение + уведомления**: покупателю «заказ принят», админу (карточка/тема), карточка на доску.

> Переходы статусов (approve/reject/ship/deliver) в REST **не вынесены** — они происходят через бота. `reject` восстанавливает сток, `deliver` — нет.

### 3.3 Админские эндпоинты
Товары: `GET /api/admin/products`, `/products/archived`, `POST /products`, `PATCH /products/{id}`, `PATCH /products/{id}/active`, `PATCH /products/{id}/archived`.
Теги: `GET/POST /api/admin/tags`, `PATCH/DELETE /tags/{id}`.
Заказы: `GET /api/admin/orders`, `GET /api/admin/orders/page` (пагинация/фильтры/сортировка + агрегаты выручки), `DELETE /orders/{id}`.
Промокоды: `GET/POST /api/admin/promocodes`, `PATCH/DELETE /promocodes/{id}`.
Шаблон оплаты: `GET/PUT /api/admin/settings/payment-template`.
Логин: `POST /api/admin/login`.

**Нюансы:** уникальность title проверяется при создании, но **НЕ при обновлении**. При обновлении товара картинки **полностью пересоздаются** (старые удаляются). Для товаров с вариантами `stock` всегда перезаписывается суммой вариантов.

### 3.4 Медиа
`GET /media/{filename}` — отдаёт байты из `media_images`, кэш `max-age=30 дней, immutable`.

## 4. Telegram-бот (самая сложная часть)

### 4.1 Базис
- `ShopBot` (long polling) — единственная точка вызова Telegram API. Все вызовы через `safeExecute(...)` — best-effort, ошибки логируются, не ломают цикл.
- **Команды:** `/start` и `/shop` → кнопка-WebApp «🛍️ Открыть магазин» (`{baseUrl}/app/index.html?mode=user`); `/help` → список команд; `/set_orders_new_topic`, `/set_orders_processing_topic`, `/set_orders_shipped_topic`, `/set_orders_closed_topic` → привязка стадий доски к forum-темам (выполнять внутри темы; только админ). **Команды `/admin` нет** — в админку входят через веб.

### 4.2 Две админ-модели уведомлений о заказе
- **Доска настроена** (есть хоть один `ADMIN_ORDER_BOARD_*`): для каждого заказа создаётся отдельная forum-тема + карточка-«доска» (одно сообщение на заказ), которое **физически переезжает между темами** при смене статуса (NEW→PROCESSING→SHIPPED→CLOSED/REJECTED).
- **Доска не настроена (legacy):** одно уведомление в админ-чат с инлайн-кнопками.

### 4.3 Мост «админ ↔ покупатель» (order-chat-bridge) — фишка проекта
Каждый заказ получает свою forum-тему в админ-группе. Бот **пересылает сообщения в обе стороны**, так что админ и покупатель «переписываются» через бота:
- **Админ пишет в тему** → бот шлёт покупателю «📩 Сообщение от администратора» (с ForceReply, чтобы поймать ответ). Медиа форвардится.
- **Покупатель отвечает реплаем** → бот постит в тему заказа «👤 Сообщение от пользователя».
- **Редактирование сообщений зеркалится** в обе стороны.
- Связка покупательского ответа с заказом держится на `replyAnchorMap` (in-memory).
- Универсальный форвардер поддерживает text/photo/document/video/audio/voice/animation/sticker/video_note/contact/location.

⚠️ **Всё состояние моста — in-memory (`BotState`, ConcurrentHashMap), теряется при рестарте.** Долговечное состояние — только поля на `OrderEntity` и `order_messages`.

### 4.4 Обработка решений по заказу (инлайн-кнопки)
Callback-и: `order:approve`, `order:reject` (→ ForceReply «причина»), `order:ship` (→ ForceReply «ТТН»), `order:invoice` (отправить покупателю реквизиты оплаты), `order:deliver`. Только для админов. После действия редактируется карточка, обновляется клавиатура по статусу, пишется системное сообщение в лог.

Кнопки по статусу: NEW → [Одобрить, Отклонить]; APPROVED → [Выслал заказ, Отклонить] + [💳 Отправить счёт]; SHIPPED → [Доставлено, Отклонить]; + [💬 В чат заказа] если есть тема.

### 4.5 Жизненный цикл (через `OrderService`)
| действие | статус | побочные эффекты |
|---|---|---|
| создать | NEW | уведомить покупателя + админа + доска |
| approve | APPROVED | уведомить покупателя, переименовать тему, доска→PROCESSING |
| ship(ТТН) | SHIPPED | ТТН, уведомить, доска→SHIPPED |
| deliver | DELIVERED | доска→CLOSED + **архив переписки (ZIP)**, удалить тему |
| reject(причина) | REJECTED | **вернуть сток**, уведомить, доска→REJECTED + архив, удалить тему |

### 4.6 Архив переписки (`OrderChatArchiveService`)
На терминальных стадиях (CLOSED/REJECTED) бот собирает **ZIP со статичным HTML-экспортом** переписки (в стиле Telegram-экспорта: тёмная тема, дни, аватары, медиа скачиваются по file_id) и отправляет документом в доску.

### 4.7 `TgPostImageResolver`
Утилита: достаёт картинки из публичных Telegram-постов (`t.me/channel/123`, `tg://resolve?...`) через Jsoup-скрейп — используется при импорте картинок товара по ссылке на пост.

## 5. Mini App покупателя (фронтенд)

UI на русском, валюта UAH. Тёмная тема **захардкожена** (не читает тему Telegram).

### 5.1 Экраны
- **Каталог** — сетка 2 колонки (3 при ≥900px). Карточка: миниатюра (ленивая загрузка, **авто-ротация** нескольких фото каждые ~5с с кросс-фейдом), название, цена, остаток, «Подробнее». Авто-рефреш каждые 15с с патчингом DOM (без прыжка скролла).
- **Карточка товара** (bottom-sheet): теги, **выбор варианта** (чипы с остатком), цена/наличие, кнопка «В корзину» / степпер `− qty +`, описание, **галерея** (свайп, стрелки, точки, полноэкранный режим с пинч-зумом, шэринг).
- **Корзина** (bottom-sheet): строки со степперами, «Очистить», итог, «Оформить заказ».
- **Оформление** (bottom-sheet, форма): ФИО, Телефон, Адрес (город + отделение Новой Почты), Промокод, Комментарий → POST `/api/orders` → экран успеха с номером заказа.
- **Сортировка** (по умолчанию / цена ↑↓ / популярные по soldCount), **Поиск** (по названию), **фильтр по тегам**.
- **Гейт браузера**: если открыто не в Telegram — блок «Откройте через Telegram-бота».

### 5.2 Интеграция с Telegram SDK
`ready()`, `expand()`, `initData` (для auth), `start_param` (диплинк на товар `product_<id>`), **MainButton** («Оформить заказ • сумма»), HapticFeedback, `openTelegramLink` (шэринг). **BackButton и themeParams НЕ используются.**

### 5.3 Чего НЕТ
- Нет истории заказов / профиля.
- Нет шага оплаты в самом приложении («К оплате» — информативно; оплата идёт через бота-«счёт»).
- Нет админ-режима в Mini App.
- Корзина в localStorage (`tgshop_cart`).

### 5.4 Текущий визуал
Тёмная «глассморфная» тема: `--bg:#0b0f14`, `--card:#121925`, акцент `--accent:#33b1ff`. Скруглённые углы (16-18px, пилюли 999px), backdrop-blur у шапки/галереи, мягкие тени. Bottom-sheet модалки. Font Awesome + эмодзи. Системный шрифт.

## 6. Веб-админка (фронтенд)

UI на русском, SPA на vanilla JS, вход по паролю (`X-Admin-Password` в каждом запросе, сохраняется в sessionStorage).

### 6.1 Вкладки (6)
1. **Каталог** — мощная **клиентская** фильтрация/сортировка/поиск (16 вариантов сортировки, фильтры по стоку/видимости/тегам, виды «строки»/«карточки», префы в localStorage). Карточка: фото, бейджи «Скрыт»/«Нет в наличии», теги, стат-полоса (Цена, Остаток, Продано, Теги, Варианты), действия (редактировать / скрыть / в архив).
2. **История покупок (Заказы)** — **серверная** пагинация (`/api/admin/orders/page`): сводные карточки (Заказы / Выручка доставленных / Доставлено), фильтры (поиск, статус, даты, сортировка, размер страницы), **таблица** (Дата, Заказ, Клиент, Контакты, Адрес, Товары, Сумма, Статус). Действие — **только удалить**.
3. **Архив** — архивные товары, кнопка «Вернуть».
4. **Теги** — создать/переименовать/удалить.
5. **Промокоды** — код, % или фикс-сумма, лимит, активность; CRUD.
6. **Шаблон оплаты** — редактор с лёгкой разметкой (`**bold**`, `//italic//`, `__underline__`, `~~strike~~`, `` `code` ``, ссылки, разделитель) + живое превью в Telegram-HTML. Строки `Карта/IBAN/Получатель/РНОКПП/Назначение платежа` авто-оборачиваются в `<pre>`.

### 6.2 Создание/редактирование товара (левая панель)
Поля: Название, Описание, Цена (default 1500), Валюта (UAH), Остаток (авто = сумма вариантов, если есть), **URL картинок** (через запятую/перенос — **только URL, без загрузки файлов!**), Варианты+остатки, Теги, чекбокс «Показывать в каталоге». «Удаление» товара = архивация (мягкое, без подтверждения).

### 6.3 Тумблер «Вид от лица покупателя»
Прячет панель добавления и админ-вкладки, грузит публичный список `/api/products`, открывает превью вместо редактора.

### 6.4 ⚠️ Главный пробел админки
В таблице заказов **нет** управления статусом, нет поля ТТН, нет «Отправить счёт», нет детальной карточки заказа — **только удаление**. Все переходы статусов делаются **только через бота в Telegram**. Бэкенд и данные это поддерживают — фронт не вытаскивает. Это очевидный кандидат на доработку (например, kanban-доска со статусами NEW→APPROVED→SHIPPED→DELIVERED).

### 6.5 Визуал
Та же тёмная тема, что и Mini App (bg `#0b0f14`, акцент `#33b1ff`), CSS Grid, скруглённые карточки/пилюли, шрифт Inter. Подтверждения — нативные `confirm()/prompt()/alert()`.

## 7. Сводка фич (чеклист для решения «брать / не брать»)

**Каталог и товары:** товары с фото-галереей и авто-ротацией · варианты с отдельным стоком · теги (M↔N) · мягкое удаление (архив) · скрытие из каталога (active) · поиск/сортировка/фильтр · картинки бинарём в БД · импорт картинок по URL и из Telegram-постов · счётчик продаж (soldCount).

**Корзина и заказ:** корзина в localStorage · промокоды (% и фикс-сумма, лимит использований) · оформление с данными Новой Почты · снимки цен/названий в заказе · списание/возврат стока · хардкод валюты UAH.

**Бот:** кнопка-WebApp · уведомления о заказе · forum-тема на заказ · **двусторонний мост админ↔покупатель** (текст+медиа, с зеркалированием правок) · доска со стадиями (карточка переезжает между темами) · инлайн-управление статусами · запрос ТТН и причины отказа через ForceReply · отправка реквизитов оплаты («счёт») · ZIP-архив переписки на закрытии.

**Админка:** вход по паролю · CRUD товаров/тегов/промокодов · серверная таблица заказов с фильтрами и выручкой · редактор шаблона оплаты с превью · вид «от лица покупателя».

**Чего нет (потенциал для нового):** история заказов у покупателя · реальная онлайн-оплата · управление заказами из веб-админки · мультивалютность · аналитика/дашборд · i18n (всё захардкожено по-русски) · адаптация под тему Telegram · загрузка картинок файлами.

## 8. Главные технические долги (учесть при переписывании)

1. Дубликат версии Flyway `V2` — перенумеровать.
2. `ddl-auto: update` + Flyway вместе; `media_images` и `admin_*`-колонки без миграций — навести порядок, Flyway как единственный источник.
3. Захардкоженные секреты в `application.yml` (IP, пароли) — вынести в обязательные env без дефолтов.
4. Всё состояние Telegram-моста in-memory — теряется при рестарте; перенести в БД, если мост остаётся.
5. Нет проверки свежести `auth_date` в initData — добавить TTL.
6. Валюта захардкожена UAH в нескольких местах.
7. Картинки бинарём в БД (LONGBLOB) раздувают дамп до 136 МБ — рассмотреть объектное хранилище (S3/диск).
8. Управление заказами разорвано: статусы только через бота, веб-админка только удаляет — свести в одно место.
