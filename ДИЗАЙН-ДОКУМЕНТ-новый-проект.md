## 0. Краткое видение нового продукта

Тот же Telegram-магазин, но:
- **Бот — тонкий слой**: только вход (кнопка `/start` → сайт) и **уведомления**. Никаких переписок и управления заказами внутри Telegram.
- **Всё происходит на сайте** (Mini App + отдельная админка): каталог, корзина, заказы, **чат с админом прямо на сайте** (в стиле Telegram-чата).
- **Покупатель авторизован через Telegram initData** (привязка к Telegram user id), **админ — через Spring Security + JWT** с аннотацией `@RequiredAdmin`.
- **Фронтенд на современном фреймворке** (Next.js), деплоится отдельно от бэкенда, liquid-glass дизайн, быстрый отклик, нормальная загрузка картинок.
- **Чат админ↔покупатель — на сайте в реальном времени** (WebSocket). Бот пингует покупателя «открыть переписку» только когда пишет **админ**.
- **Админ-уведомления — в мультигруппе с тематическими каналами**: заказы прилетают в каналы по статусу, с кнопкой «Открыть в админке», при смене статуса карточка переезжает между каналами.

## 1. Целевая архитектура

```
                         ┌──────────────────────────┐
   Telegram  ──/start──> │  Bot (тонкий)            │
                         │  • кнопка-WebApp → сайт  │
                         │  • уведомления клиенту   │
                         │  • уведомления в каналы  │
                         └────────────┬─────────────┘
                                      │ (вызывает Notification API внутри бэка)
 ┌─────────────┐   REST + WS   ┌──────┴───────────┐   JPA   ┌──────────┐
 │ Mini App     │ ───────────> │  Spring Boot API  │ ──────> │  MySQL   │
 │ (Next.js)    │ <─WebSocket─ │  • Security + JWT  │         └──────────┘
 │ покупатель   │              │  • REST controllers│
 └─────────────┘              │  • WS (чат)        │   S3 API  ┌──────────────┐
 ┌─────────────┐   REST + WS   │  • Bot module      │ ────────> │ Object Store │
 │ Admin Web    │ ───────────> │                    │           │ (картинки)   │
 │ (Next.js)    │ <─WebSocket─ └────────────────────┘           │  + CDN       │
 │ админ        │                                               └──────────────┘
 └─────────────┘
```

**Разделение фронта и бэка** — да. Фронт (Next.js) — самостоятельное приложение/контейнер, общается с бэком только по REST + WebSocket. Это даёт: независимый деплой, нормальный кэш/CDN на фронте, возможность хостить статику на edge.

**Realtime** — WebSocket (STOMP поверх SockJS) для чата заказов и live-обновлений статусов/каталога. Fallback — SSE/long-poll.

## 2. Технологический стек

### 2.1 Бэкенд — **сохраняем Java 21 + Spring Boot** (ты его знаешь, я в нём силён, оно уже работает)
- Spring Boot (актуальный), модули: `web`, `validation`, `data-jpa`, **`security`** (новое), `websocket` (новое).
- **Spring Security + JWT** — `io.jsonwebtoken (jjwt)` или `spring-security-oauth2-resource-server` (JWT resource server). Рекомендую resource-server подход — меньше своего кода.
- MySQL 8.4 + Flyway (как единственный источник схемы).
- telegrambots (как и было) — но бот сильно упрощается.
- Jsoup — оставить только если нужен импорт картинок из Telegram-постов.
- **springdoc-openapi** (`springdoc-openapi-starter-webmvc-ui`) — **Swagger UI** на `/swagger-ui.html` + OpenAPI JSON. Документировать все эндпоинты, схемы DTO, авторизацию (Bearer JWT).
- **Thymeleaf** — **красивый хоум-пейдж** на `/`: ссылки на Swagger, на фронтенд, версия билда/коммит, аптайм, статус БД/кэшей, ссылки на Actuator. (Версию билда отдавать через `spring-boot-maven-plugin build-info` → `/actuator/info`.)
- **Spring Boot Actuator** — `/actuator/health`, `/actuator/info` (версия билга), `/actuator/caches`, `/actuator/metrics`. Эндпоинты Actuator закрыть под ADMIN (кроме health).
- **Кэш** (`spring-cache` + Caffeine) — для справочника отделений Новой Почты, app-info, тяжёлых выборок. Виден в `/actuator/caches`.
- **Планировщик** (`@Scheduled`) — ежедневный синк отделений Новой Почты (§9bis).
- **Тесты** — добавить (старый проект собирался с `-DskipTests`, тестов нет).

### 2.2 Фронтенд — **Next.js 15 (App Router) + TypeScript** ⭐ рекомендация
Почему именно он под твои требования:
| Требование | Как закрывает Next.js |
|---|---|
| Очень быстрый отклик | App Router + React Server Components + кэш `TanStack Query`; prefetch, оптимистичные апдейты |
| Проблема с картинками | `next/image` (или кастомный `<Image>`): responsive `srcset`, WebP/AVIF, lazy-load, blur-up плейсхолдеры (LQIP), приоритетная загрузка первого экрана |
| Запуск отдельно от бэка | Самостоятельный деплой (свой контейнер / Vercel), к API ходит по REST/WS |
| Гибкость под нужды | Огромная экосистема, легко добавить чат, формы, анимации |
| Я скилловый и без проблем подниму | React/Next — мой сильнейший стек |
| Liquid glass без дефолтных инпутов | Tailwind CSS v4 + кастомная дизайн-система, все контролы свои |

**Сопутствующее:**
- **Tailwind CSS v4** — дизайн-токены и утилиты (вся liquid-glass система на CSS-переменных + кастомные утилиты).
- **TanStack Query** — кэш данных, фоновые ре-фетчи, оптимистичные мутации (быстрый UX).
- **`@telegram-apps/sdk-react`** — современный SDK Mini App (initData, тема, кнопки, haptics, viewport).
- **Framer Motion** — плавные анимации (открытие шторок, переходы, «жидкие» хайлайты).
- **TanStack Virtual** — виртуализация длинных списков (каталог, история сообщений) для скорости.
- Иконки — Lucide (чистые SVG, tree-shakeable).

> Альтернатива (если захочется максимально лёгкий бандл): **SvelteKit** — меньше вес, быстрее на слабых телефонах. Но экосистема и моя глубина — больше в Next.js, поэтому по умолчанию беру Next.js. Финальное слово за тобой (см. §12 «Открытые вопросы»).

### 2.3 Хранилище картинок — **self-hosted, всё в Docker на твоём сервере** (без облаков)
Условие: один Linux-сервер, всё в Docker, никаких Cloudflare/AWS. Решение — полностью свой стек из 3 контейнеров:

```
браузер ──> Nginx (disk cache) ──> imgproxy (ресайз/WebP/AVIF) ──> MinIO (хранит оригиналы)
```

1. **MinIO** (S3-совместимое хранилище) — контейнер, хранит **оригиналы** картинок в Docker-томе (bucket `product-images`). Приложение заливает туда через обычный **S3 SDK** (AWS SDK for Java / MinIO SDK) — код портативный, при желании потом легко переехать на настоящий S3.
2. **imgproxy** — контейнер, **on-the-fly ресайз и конвертация**: читает оригинал из MinIO (S3-источник), отдаёт нужный размер в **WebP/AVIF**, обрезку, качество. URL подписываются ключом (защита от абуза). Лёгкий и очень быстрый (Go).
3. **Nginx** перед imgproxy с **`proxy_cache` на диск** — кэширует уже обработанные картинки, повторные запросы отдаются мгновенно, без повторной обработки. Заголовки `Cache-Control: immutable, max-age=1y` (ключ кэша — по контент-хэшу/пути, поэтому при замене картинки URL меняется).

**Поток:** загрузка товара → приложение кладёт оригинал в MinIO (ключ = хэш контента) → во фронт отдаётся URL вида `/img/<signature>/rs:fill:600:600/plain/s3://product-images/<key>@webp` → Nginx (кэш) → imgproxy (только при промахе) → MinIO.

**Почему это чинит текущий непрогруз:** сейчас картинки — LONGBLOB, тянутся синхронно из MySQL через Java-приложение (медленно, грузит и БД, и app, дамп раздут до 136 МБ). Новый стек: оригиналы вне БД, отдача статикой через Nginx-кэш + готовые мелкие WebP под устройство → быстро и не нагружает приложение.

**Бэкап:** том MinIO бэкапится отдельно (или `mc mirror`); БД больше не раздувается картинками.

> Более лёгкая альтернатива (если не хочешь даже MinIO): imgproxy умеет читать прямо с **локального тома** (`local://`), тогда оригиналы просто лежат в папке-томе, а MinIO не нужен — но теряешь S3-абстракцию и аккуратные бэкапы. По умолчанию беру вариант с MinIO.

## 4. Авторизация (Spring Security + JWT)

### 4.1 Покупатель — авторизован через Telegram initData
Поток:
1. Mini App при старте берёт `initData` из Telegram SDK.
2. `POST /api/auth/telegram` с initData → бэк проверяет **HMAC-SHA256** (как в старом `TgInitDataValidator`) **+ TTL `auth_date`** (новое — старый не проверял свежесть).
3. Бэк находит/создаёт `User` по `telegram_user_id`, выдаёт **короткоживущий access JWT** (роль `CUSTOMER`, subject = telegram user id) + опционально refresh.
4. Фронт хранит JWT (в памяти / sessionStorage), шлёт в `Authorization: Bearer ...`.
5. Все покупательские эндпоинты требуют валидный CUSTOMER-JWT; ресурсы привязаны к `telegram_user_id` из токена (свои заказы, свой чат).

> Преимущество: initData проверяется один раз, дальше — обычный stateless JWT. Привязка ко всем данным покупателя по user id из токена.

### 4.2 Админ — Spring Security + JWT + `@RequiredAdmin`
**Вход админа** (рекомендация — через Telegram, без паролей):
- Вариант A (рекомендую): админ открывает админку, логинится **Telegram Login Widget** или через тот же initData (если открывает админку из бота). Бэк проверяет, что `telegram_user_id ∈ admin_users` → выдаёт **ADMIN-JWT** (роль `ADMIN`).
- Вариант B (запасной): классический логин e-mail/пароль (bcrypt) для standalone-входа без Telegram.

**Аннотация `@RequiredAdmin`:**
```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("hasRole('ADMIN')")
public @interface RequiredAdmin {}
```
- Включаем `@EnableMethodSecurity`.
- Вешаем `@RequiredAdmin` на админ-контроллеры/методы.
- `SecurityFilterChain`: stateless, JWT-фильтр валидирует токен и кладёт `Authentication` с ролями. Без валидного JWT нужной роли — 401/403.
- Таблица `admin_users(telegram_user_id, name, role, active, created_at)` — источник прав (вместо строки `ADMIN_USER_IDS` в конфиге; конфиг можно оставить как сидер первого админа).

### 4.3 Что чинит
- Убирает «тупой заголовок» `X-Admin-Password` и пароль `admin123` в конфиге.
- Единый Security-слой, роли, аннотации, нормальные 401/403.
- initData проверяется с TTL, дальше stateless.

## 5. Новая механика бота

Бот максимально тонкий. Никакой бизнес-логики/чатов внутри Telegram.

### 5.1 Сторона покупателя
- `/start` → приветствие + кнопка-WebApp «🛍️ Открыть магазин» → открывает сайт.
- На сайте у покупателя две основные зоны: **Магазин** и **Мой аккаунт** (вкладка):
  - **Мой аккаунт → Мои заказы**: список заказов (статус, сумма, дата, кол-во позиций).
  - Открытие конкретного заказа → **детальная карточка** (состав, суммы, статус, ТТН, адрес) + сверху кнопка **«💬 Чат заказа»**.
  - **Чат заказа** — переписка с админом прямо на сайте, в стиле Telegram (реплаи, эмодзи, фото/вложения, статусы доставки/прочтения).
- **Бот пингует покупателя ТОЛЬКО когда пишет админ**: когда админ отправляет сообщение в чат заказа → бот шлёт покупателю новое сообщение в Telegram: «💬 Новое сообщение по заказу #1234» + кнопка **«Открыть переписку»** (диплинк в Mini App прямо на чат этого заказа). Когда покупатель сам пишет — бот его не пингует.
- Опционально бот шлёт уведомления о смене статуса заказа («✅ Заказ одобрен», «📦 Выслан, ТТН …», «🎉 Доставлен»).

### 5.2 Сторона админа — мультигруппа с тематическими каналами
- Супергруппа с **темами-каналами по статусам**: «🆕 Новые», «🛠 В обработке», «📦 Выслан», «✅ Закрытые/Отклонённые» (привязка через настройки, как старые `ADMIN_ORDER_BOARD_*`).
- Новый заказ → карточка в канал «Новые»: краткая инфа о заказе + кнопка **«🔎 Открыть в админке»** (URL на страницу заказа в админ-сайте) + опц. «💬 Открыть чат».
- **При смене статуса** карточка **удаляется из старого канала и постится в новый** (механика «переезда» из старого проекта сохраняется, но это чисто уведомление).
- **Управление заказом — на сайте**: админ жмёт «Открыть в админке» → страница заказа с кнопками управления (Одобрить/Выслать+ТТН/Доставлено/Отклонить+причина/Отправить счёт) и встроенным чатом с клиентом. Никаких инлайн-кнопок управления в Telegram.

### 5.3 Что упрощается
- Уходит весь in-memory мост (`BotState`, reply-anchor, зеркалирование правок) — он был хрупким (терялся при рестарте).
- Бот не хранит состояние переписки — всё в БД и на сайте.

## 6. Чат заказа на сайте (ключевая новая фича)

### 6.1 Хранилище (развитие `order_messages`)
Таблица `order_messages` расширяется:
- `id, order_id, sender_type (CUSTOMER|ADMIN|SYSTEM), sender_id, sender_name`
- `type (TEXT|PHOTO|FILE|SYSTEM)`, `text`, `attachment_url`, `file_name`, `mime_type`, `width/height` (для фото-превью)
- `reply_to_message_id` (реплаи)
- `reactions` (json: emoji → list of user) — опционально
- `created_at`, `delivered_at`, `read_at` (статусы прочтения)
- индексы по `order_id, created_at`.

### 6.2 Realtime
- WebSocket-топик на заказ: `/ws/orders/{orderId}/chat`. Подписка проверяет права (владелец заказа или админ).
- Отправка сообщения → сохраняется в БД → пушится подписчикам → обновляются непрочитанные.
- Когда **админ** отправил и **покупатель оффлайн** (нет активной WS-сессии) → триггерится бот-пинг (§5.1).

### 6.3 UI чата — «закосить под Telegram»
- Пузыри сообщений: входящие слева, исходящие справа (акцентный glass-пузырь).
- Реплаи (свайп/клик «ответить», цитата над сообщением).
- Эмодзи-пикер, реакции на сообщения.
- Вложения: фото с превью и лайтбоксом, файлы с иконкой и размером, прогресс загрузки.
- Статусы: отправлено/доставлено/прочитано (галочки), индикатор «печатает…», таймстемпы, разделители по дням.
- Автоскролл к новым, «↓ N новых», виртуализация длинной истории.

## 6bis. Оформление заказа (степпер), доставка и оплата

### 6bis.1 Чекаут пошаговый (wizard)
Оформление — не одна простыня, а **шаги** с прогресс-индикатором (стеклянный степпер), валидация на каждом шаге, можно вернуться назад:
1. **Корзина** — обзор позиций, кол-во, промокод, итог.
2. **Контакты** — ФИО, телефон (с маской).
3. **Доставка** — выбор способа (см. 6bis.2).
4. **Оплата** — выбор предпочтительного варианта оплаты (см. 6bis.3).
5. **Подтверждение** — сводка всего заказа → «Оформить».
6. **Готово** — экран успеха + номер заказа + что дальше (реквизиты/ожидание подтверждения).

### 6bis.2 Доставка — 2 опции
- **Новая Почта (приоритет)**: выбор **города** (автокомплит) → выбор **отделения/почтомата** (автокомплит из локального справочника, см. §9bis). Сохраняем в заказ город + отделение (номер/адрес + ref НП).
- **Самовывоз**: без адреса (или фикс-точка самовывоза из настроек магазина).
- Способ доставки и его детали сохраняются на заказе; в карточке заказа (и у покупателя, и у админа) видно способ + отделение.

### 6bis.3 Оплата — выбор варианта (комиссий платёжкам не платим)
Онлайн-эквайринг **не подключаем** (по твоему решению). Вместо этого:
- Админ настраивает **список вариантов оплаты** (в настройках магазина), сейчас в базе их два:
  - **Вариант 1 — предоплата 100 грн** (бронь товара + бесплатная доставка).
  - **Вариант 2 — полная оплата на карту.**
  - + реквизиты (карта `4246001040134680`, IBAN `UA66...8119`, РНОКПП `3547612413`, назначение платежа).
- Покупатель **на шаге «Оплата» видит варианты и выбирает предпочтительный**; выбранный вариант сохраняется на заказе.
- После оформления покупателю показываются **реквизиты под выбранный вариант** (на сайте + при необходимости через бота). Подтверждение оплаты — как и раньше, через чат заказа / вручную админом.
- **Модель данных:** настройки `payment_options` (список: id, title, description, нужна ли предоплата/сумма) + `payment_requisites` (карта/IBAN/получатель/РНОКПП/назначение). Заказ получает `payment_option_id` (выбор покупателя). Старый `PAYMENT_TEMPLATE_HTML` → мигрируем в структурированные `payment_options` + `payment_requisites` (с редактором в админке и превью).

## 6ter. Админка: канбан-доска заказов (десктоп) + мобильный вид

Главный экран управления заказами в админке — **канбан-доска** (по твоей идее): наглядно видно, какие заказы в каком статусе, перетаскиванием меняешь статус, кликом разворачиваешь заказ на весь экран с деталями и чатом.

### 6ter.1 Десктоп — доска
- **Колонки = статусы заказа**: `🆕 Новые` → `✅ Одобрены` → `📦 Выслан` → `🎉 Доставлен` → `❌ Отклонён` (последняя колонка может быть свёрнута/в отдельной вкладке, чтобы не засорять).
- **Карточка заказа в колонке** (компактная, стеклянная): № заказа, имя клиента, сумма, кол-во позиций, время, бейдж способа доставки (НП/самовывоз), бейдж варианта оплаты, **бейдж непрочитанных сообщений** в чате, мини-аватар/иконка.
- **Drag & Drop между колонками** = смена статуса. Библиотека — **dnd-kit** (React; доступная, быстрая, тач-френдли).
  - При перетаскивании в `📦 Выслан` → всплывает запрос **ТТН** (обяз.).
  - При перетаскивании в `❌ Отклонён` → запрос **причины** (обяз.) + возврат стока.
  - Переходы валидируются (нельзя из «Доставлен» назад и т.п.) — подсветка допустимых колонок при драге.
  - **Оптимистичный апдейт** (карточка сразу переезжает) + откат при ошибке сервера.
- **Хедер колонки**: счётчик заказов + сумма по колонке (напр. выручка в стадии).
- **Тулбар доски**: поиск, фильтр по датам/способу доставки/оплате, переключатель **«Доска / Таблица»** (таблицу-вид из старого проекта сохраняем как альтернативу для плотных данных и экспорта).
- **Realtime (WebSocket)**: новый заказ влетает в колонку «Новые» live; если статус меняют из бота/другого админа — доска обновляется без рефреша.

### 6ter.2 Разворот заказа (клик по карточке)
Клик → заказ **разворачивается на весь экран** (drawer справа на широком экране / full-screen на узком). Внутри:
- **Шапка**: № заказа, статус (с быстрым переключателем статуса), дата.
- **Детали**: клиент (имя, телефон, @username, Telegram-ссылка), состав заказа (позиции со снимками, варианты, кол-во, цены), суммы (subtotal/скидка/промокод/итог), **способ доставки** (НП: город + отделение / самовывоз), **выбранный вариант оплаты**, комментарий.
- **Таймлайн статуса** (Принят → Одобрен → Выслан(ТТН) → Доставлен) с временами.
- **Кнопки управления**: Одобрить / Выслать (+ТТН) / Доставлено / Отклонить (+причина) / Отправить реквизиты («счёт»). Те же переходы, что и драг, но кнопками.
- **Чат с клиентом** — встроен прямо в разворот (тот же компонент чата, что у покупателя, §6): переписка в реальном времени, вложения, реплаи. Когда админ пишет — клиенту летит пинг в бота (§5.1).

### 6ter.3 Мобильный вид доски (чтобы ничего не развалилось)
На телефоне колонки рядом не помещаются → доска превращается в **список с сегментами-статусами**:
- Сверху — горизонтальный **сегмент-контрол статусов** (свайпаемые табы: Новые / Одобрены / Выслан / Доставлен / Отклонён) со счётчиками.
- Под активным статусом — вертикальный список карточек заказов.
- Смена статуса — **не драгом**, а кнопкой «Переместить в…» (bottom-sheet со списком допустимых статусов) или свайпом по карточке.
- Тап по карточке → **full-screen** карточка заказа + чат (как в 6ter.2, но на весь экран).
- Итог: на десктопе — красивый канбан с драгом, на телефоне — удобный таб-список, функционал тот же, ничего не уезжает.

## 8. Дизайн-система «Liquid Glass» (детально)

> Цель: дорогой стеклянно-жидкий интерфейс (в духе Apple Liquid Glass 2025): полупрозрачные слои с размытием и подсветкой граней, мягкая глубина, плавные «текучие» переходы. **Никаких дефолтных HTML-инпутов** — все контролы кастомные. Адаптация под light/dark и акцент темы Telegram.

### 8.1 Принципы
1. **Материал, а не плоскость**: поверхности — это «стекло» (blur + полупрозрачный фон + бликовая грань + тень), лежащее над живым фоном.
2. **Слои и глубина**: фон → контент → плавающие стеклянные панели (шапка, шторки, таб-бар, чат-композер).
3. **Текучесть**: переходы и хайлайты «перетекают» (spring-анимации, морфинг активного таба, мягкие масштабы при нажатии).
4. **Содержимое — король**: стекло обрамляет, не перекрикивает; контраст текста всегда выдержан поверх блюра.
5. **Адаптивность к теме**: токены завязаны на light/dark и на `themeParams` Telegram (акцент пользователя).

### 8.2 Токены (CSS-переменные)
```css
:root {
  /* фон сцены (под стеклом) — мягкий градиентный «живой» бэкграунд */
  --bg-scene: radial-gradient(120% 120% at 0% 0%, #1b2330 0%, #0c1118 60%);

  /* стекло */
  --glass-bg:        rgba(255,255,255,0.08);   /* заливка панели */
  --glass-bg-strong: rgba(255,255,255,0.14);   /* акцентные/верхние слои */
  --glass-stroke:    rgba(255,255,255,0.22);   /* верхняя бликовая грань */
  --glass-stroke-bottom: rgba(0,0,0,0.25);     /* нижняя теневая грань */
  --glass-blur: 20px;
  --glass-saturate: 160%;

  /* акцент (дефолт; перетирается themeParams Telegram) */
  --accent: #5ac8fa;
  --accent-ink: #00131c;        /* текст на акценте */

  /* текст */
  --text:        rgba(255,255,255,0.96);
  --text-muted:  rgba(255,255,255,0.62);
  --text-faint:  rgba(255,255,255,0.40);

  /* семантика */
  --ok: #34c759; --warn: #ff9f0a; --danger: #ff453a;

  /* геометрия */
  --r-sm: 12px; --r-md: 18px; --r-lg: 26px; --r-pill: 999px;

  /* тени глубины */
  --shadow-1: 0 6px 20px rgba(0,0,0,.28);
  --shadow-2: 0 16px 48px rgba(0,0,0,.40);
}
```
Light-режим — отдельный набор (стекло на тёмном тексте, `--glass-bg: rgba(255,255,255,0.55)` и т.п.). Переключение по `prefers-color-scheme` + по теме Telegram.

### 8.3 Базовый «стеклянный» класс
```css
.glass {
  background: var(--glass-bg);
  backdrop-filter: blur(var(--glass-blur)) saturate(var(--glass-saturate));
  -webkit-backdrop-filter: blur(var(--glass-blur)) saturate(var(--glass-saturate));
  border-radius: var(--r-md);
  border: 1px solid transparent;
  /* двойная грань: светлый верх + тёмный низ через border-image/inset-тени */
  box-shadow:
    inset 0 1px 0 var(--glass-stroke),
    inset 0 -1px 0 var(--glass-stroke-bottom),
    var(--shadow-1);
}
.glass--floating { box-shadow: inset 0 1px 0 var(--glass-stroke), var(--shadow-2); }
```
Опционально — едва заметный шум (`.glass::after` с SVG-noise, opacity ~0.03) против бандинга блюра + спекулярный блик-«хайлайт» при наклоне (parallax на акселерометр/курсор).

### 8.4 Компоненты (все кастомные, без дефолтных тегов)
- **Кнопки**: `.btn-glass` (стеклянная), `.btn-accent` (заливка акцентом, текст `--accent-ink`), `.btn-ghost`. Нажатие — `scale(.97)` + усиление блика (spring). Иконка+текст, состояние loading со спиннером.
- **Инпуты/текстарии**: кастом-обёртка `.field` — стеклянный контейнер, плавающий лейбл, фокус-кольцо акцентом, валидация (цвет грани → danger/ok), без браузерного `outline`. Маски для телефона.
- **Селекты/дропдауны**: кастомные (не нативный `<select>`) — стеклянное меню, поиск, клавиатурная навигация.
- **Чекбоксы/тогглы**: кастомные «пилюли» с текучим переключением.
- **Чипы/теги**: стеклянные пилюли; активный — заливка акцентом; для фильтров и вариантов.
- **Карточка товара**: стеклянная, фото с blur-up, бейджи (скидка/нет в наличии/хит), микро-ховер подъём.
- **Bottom sheets / модалки**: плавающее стекло снизу, ручка-«грабер», spring-выезд, дим-фон с блюром, свайп-закрытие.
- **Таб-бар** (Магазин / Заказы / Аккаунт): нижний стеклянный, активный таб с «жидким» морфирующим хайлайтом (Framer Motion `layoutId`).
- **Шапка**: стеклянная sticky с блюром, прячется при скролле вниз.
- **Степпер количества**, **галерея** (свайп, точки, фуллскрин-зум), **тосты** (стеклянные), **скелетоны** загрузки (shimmer).
- **Чат**: пузыри-стекло, акцентный пузырь исходящих, реплай-цитаты, реакции, превью вложений, индикатор печати, галочки прочтения.

### 8.5 Типографика и сетка
- Шрифт: системный SF/Segoe/Roboto стек или Inter; крупные заголовки 600–700, тело 400–500.
- Скругления крупные (см. токены), щедрые отступы, тонкие грани.
- Сетка каталога: 2 колонки (мобайл), 3–4 на ширине.

### 8.6 Движение
- Spring-анимации (Framer Motion): открытие шторок, морфинг табов, hover/press, появление сообщений чата.
- Длительности 180–320мс, ease «жидкий» (overshoot небольшой).
- Уважать `prefers-reduced-motion`.

### 8.7 Производительность стекла
- `backdrop-filter` дорогой — ограничить число одновременно блюрящих слоёв (шапка, таб-бар, активная шторка), не вешать на каждую карточку.
- `will-change`/`transform: translateZ(0)` точечно; тестировать на слабых Android.

## 8bis. Адаптивность: клиент mobile-first, админка desktop-first

Две разные стратегии под две аудитории.

### 8bis.1 Mini App покупателя — **mobile-first**
Продажи идут в Telegram → основной экран это телефон в Telegram-webview (~360–420px).
- Проектируем сразу под узкий экран: одна колонка / сетка 2 колонки для каталога.
- Нижний **таб-бар** (Магазин / Корзина / Аккаунт), **MainButton** Telegram для главного действия, **bottom-sheet** модалки, свайпы.
- Тач-таргеты ≥44px, крупные тапы, никаких ховер-зависимых действий.
- Учитываем safe-area (вырезы), динамический viewport Telegram (`viewport-stable-height`), клавиатуру при вводе.
- На планшете/десктопе тоже не разваливается: контент в **центрированном контейнере** с max-width (~480px), по бокам — фон-сцена. Но приоритет и вся отладка — телефон.

### 8bis.2 Админка — **desktop-first, но полностью продумана под телефон**
Админ работает в основном с компа → богатые многоколоночные раскладки (канбан, сайд-панели, таблицы, плотные данные), целевая ширина 1280px+. **При этом всё обязано аккуратно сжиматься до телефона** — ничего не уезжает:
| Элемент (десктоп) | Поведение на узком экране |
|---|---|
| Боковое меню/навигация | сворачивается в drawer (гамбургер) |
| Канбан-доска (колонки) | → таб-список по статусам (см. §6ter.3) |
| Таблица заказов | → карточки-список ИЛИ горизонтальный скролл со «липкой» первой колонкой |
| Двухколоночная форма товара | → одна колонка |
| Сайд-панель/разворот заказа | → full-screen sheet |
| Модалки | → full-screen на телефоне |
| Тулбары фильтров (в ряд) | → сворачиваются в «Фильтры» (bottom-sheet) |

- **Брейкпоинты** (Tailwind по умолчанию): `sm 640 / md 768 / lg 1024 / xl 1280`. Канбан-драг включается с `lg+`, ниже — таб-список.
- Правило: **нет случайного горизонтального скролла**; единственный намеренный горизонтальный скролл — широкие таблицы (и то с липкой колонкой).
- Тестировать админку и на 1440px, и на 390px — обе крайности.

## 9. Фикс производительности картинок (отдельно, т.к. боль)

Причина текущего непрогруза: картинки — LONGBLOB в MySQL, тянутся синхронно через приложение, без кэша, дамп раздут до 136 МБ. Инфраструктурное решение — self-hosted MinIO + imgproxy + Nginx-кэш (см. §2.3). Дополнительно:

1. **Миграция блобов** из `media_images` в MinIO — одноразовый скрипт (читает блобы, заливает в bucket, переписывает `product_images.url`).
2. **Отдача с ресайзом** (imgproxy за Nginx-кэшем): `srcset` под плотность/ширину, WebP/AVIF, кэш по контент-хэшу (immutable).
3. **Фронт**: кастомный `<Image>` (с imgproxy-loader для `next/image`): lazy-load, `priority` для первого экрана, **LQIP/blur-up** плейсхолдеры (крошечный base64 из imgproxy), фиксированные размеры (нет layout shift).
4. **Загрузка товара**: drag&drop файлов + (опц.) импорт по URL/из Telegram-поста; на бэке — заливка оригинала в MinIO, ресайзы делает imgproxy по запросу.
5. Предзагрузка соседних фото в галерее (как в старом проекте — перенести).

## 9bis. Интеграция Новой Почты (справочник отделений)

Цель: на шаге доставки покупатель выбирает город и отделение/почтомат **мгновенно**, без тормозов.

- **Метод `getWarehouses`** API Новой Почты (`https://api.novaposhta.ua/v2.0/json/`) — без ключа можно тянуть полный справочник. Справочник большой → **НЕ дёргать на лету**.
- **Ежедневный синк** (`@Scheduled`, раз в сутки): фоновая задача скачивает полный справочник отделений (постранично) и сохраняет в таблицу `nova_poshta_warehouses` (+ города). Хранить `updated_at`, делать upsert.
- **Раздача на фронт**: эндпоинты `GET /api/np/cities?q=...` и `GET /api/np/warehouses?cityRef=...&q=...` — отдают из локальной БД/кэша (Caffeine), быстрый автокомплит. Видно в `/actuator/caches`.
- На заказе сохраняем `ref` города и отделения (для интеграций/печати ТТН в будущем) + человекочитаемые имена.
- На будущее (💡): тот же API умеет создавать экспресс-накладные (ТТН) — позже можно автоматизировать создание ТТН из админки.
