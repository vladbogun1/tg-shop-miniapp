# 00. Инвентаризация: где в админке ИИ используется вручную и где мог бы помочь

Основа: прод v3.50.0 (read-only копия `_worktrees/prod-ref`), бэкенд-модуль ИИ из ветки `feat/ai-assist` (UI там нет), цифры из базы прода от 07.11.2026 (только счётчики, без персональных данных).
Пути ниже — от `_worktrees/prod-ref/`; `FE` = `frontend-admin/features`.

## 0. Главное за минуту

- Ручного ИИ в админке ровно **4 потока и 5 промптов**: карточки (мастер на много товаров и окно на один товар — один и тот же промпт), поставка (шаг 1 «прочитай накладную», шаг 2 «сопоставь с каталогом»), переводы. Больше нигде по `ChatGPT/prompt/промпт` ничего нет (кроме поля «Подсказка для ИИ» у характеристики, `FE/catalog/ui/attribute/AttributeDialog.tsx:195` — это текст, который уходит в промпт карточек).
- Все 4 потока устроены одинаково: **собрать промпт → скопировать → вставить в чужой чат → вставить ответ → разбор + проверка → ревью → запись**. Значит, встроенный ИИ можно вставить **одним звеном в начало**: кнопка «Заполнить с ИИ» заменяет шаги «скопировать» и «вставить», а разбор, проверка, ревью и запись остаются прежними. Это уже сказано в плане (`memory/ai-assist-2026-11.md`, п.2) — инвентаризация его подтверждает.
- Самое дорогое по ручной работе: **карточки** (пакеты по 4–8 товаров, каждый пакет в новом чате) и **ИИ-поставка** (два захода в чат, накладная прикладывается файлом).
- Самое неудобное: копирование больших текстов (на телефоне особенно), оборванные по длине ответы («остановись на границе товара, я попрошу продолжить»), мёртвые/чужие ссылки на фото (проверяются только после скачивания), ручной ввод «какая модель ответила».
- Данные прода, которые задают масштаб (07.11): 630 товаров в базе, 277 активных; карточки: 306 готовых, 161 черновик, 2 «Проверить»; 80 товаров создано за 30 дней, 11 «незавершённых»; 5 поставок за 30 дней, 65 строк, 4 поставщика, 42 запомненных соответствия; переводов uk/en по ~750, из них 99 % уже `origin=AI`; в чате поддержки за 30 дней 161 ответ админов (и 158 сообщений клиентов); отзывов 131, с публичным ответом магазина — 1; шаблонов ответов 5.

## 1. Ручные ИИ-потоки (подробно)

Общее для всех: чат ИИ выбирает человек (в подсказках: ChatGPT, Claude, Gemini, Perplexity), ключей нет, разбор ответа — наши парсеры, они чинят висячие запятые, «умные» кавычки и оборванный ответ (`FE/cards/model/parse.ts`, `FE/supply/model/ai/parse.ts`, `FE/translation/model/parse.ts`). Если ответ не читается — человек сам просит ИИ повторить.

## 2. Бэкенд, на который опираемся (ветка `feat/ai-assist`, не на проде)

- `POST /api/admin/ai/jobs` `{feature, prompt, effort low|medium|high, researchItems 0..10}` → задача `RUNNING`; `GET /jobs/{id}` → `DONE` с ответом, стоимостью, токенами, числом поисков/страниц; `GET /status`; `POST /search-test`. Доступно любому админу (`AdminAiController`).
- Цепочка: MiniMax M3.1 Flash (таймаут 180 с, повтор 1 раз на сеть/502–504 и 1 раз на 429/529) ← агент с инструментами `search` (SearXNG → Serper; упавший провайдер отдыхает 10 мин) и `open_page` (свой загрузчик → r.jina.ai); бюджет 3 поиска и 4 страницы на товар; битый JSON — один ход-починка; журнал `ai_usage` (токены, цена, OK/EMPTY/FAILED); месячный лимит `AI_MONTH_LIMIT_CENTS` (по умолчанию $10) проверяется перед каждым вызовом модели.
- Задачи живут **в памяти процесса** (кэш на час; 3 одновременно, 10 в очереди, дальше «ИИ занят»). Следствия для UI: перезапуск бэкенда (выкатка без даунтайма поднимает копию контейнера, см. `zero-downtime-deploy-2026-11.md`) теряет текущие задачи; привязки «кто запустил, к какому товару» на сервере нет — её держит интерфейс или новая таблица.
- Замер: карточка с поиском, effort medium — ≈88 % полей совпали с эталоном ChatGPT, ≈0,20 ₴ (~$0,005), 30–60 с; накладная Taobao из 3 скринов (low) — 6/6 строк, 8 с, 0,08 ₴. Слабые места: не открывает официальную страницу, путает единицы (256000 вместо 256), оставляет пустым редкое; ChatGPT тоже ошибается.
- Чего в контракте пока **нет**: привязки результата к сущности (`productId`, `batchId`), отмены задачи, автора-админа (проверить поле в `ai_usage`), раздельных лимитов (на админа, на день, на функцию), приоритетов («карточка важнее перевода»).

## 5. Ограничения и решения владельца, которые нельзя нарушить
1. Ручной путь **остаётся** (DECISIONS: ИИ-перевод — вернуть шаги «Ответ» и «Проверка»; ИИ-поставка — «всё как в старом»). Встроенный ИИ не заменяет его, а становится основным.
2. Нет автопубликации: карточки идут в `AI_FILLED`/`READY` по порогам 80/40, товар из поставки — скрытый черновик, переводы — «Проверить ИИ».
3. «Не костыли», единые решения: один движок задач, одна проверка ответа, один журнал, а не своё на каждый экран.
4. Админка только на русском; без маскота-качка в новых визуалах; на телефоне всё работает (тач-цели ≥ 44 px, шторки вместо поповеров).
5. Выкатка без даунтайма пересоздаёт контейнер: задачи в памяти нельзя считать надёжным хранилищем.
6. Миграции: `ai_usage` из V83 → V86 при слиянии; всё новое для UI — V87+ (Нова пошта тоже V87+, согласовать порядок).

## 6. Открытые вопросы для следующих ролей
1. Где живёт «основной вход»: кнопка на каждом экране (карточка, поставка, перевод) или единый «ИИ-помощник» («кинул что угодно», как в плане)? Макеты есть только для первого варианта.
2. Нужна ли **постоянная очередь задач** (таблица вроде `ai_jobs`: кто, какая сущность, статус, результат) вместо кэша в памяти? Без неё нельзя «запустить 40 карточек и уйти».
3. Лимиты: сейчас один месячный глобальный; нужны ли на админа, на день, по функции, и что показывать при исчерпании (переход на ручной путь = запасной сценарий).
4. Что считать «качеством»: доля принятых без правок полей, число красных полей, доля авто-`READY` — какие из них пишем в журнал (`card_meta.model` уже есть).
5. Уведомление о завершении долгих задач: push в приложение уже есть (`FE/notification`, `FE/settings/ui/device/PushBlock.tsx`) — подключать ли.
6. Цены конкурентов (кандидат 11) и черновики ответов клиентам (кандидат 7) — брать ли вообще и в каком режиме.
