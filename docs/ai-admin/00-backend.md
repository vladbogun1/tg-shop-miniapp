# 00. Бэкенд ИИ: что есть и чего не хватает

Разведка 07.11.2026. Ветка `feat/ai-assist` (не на проде; миграция V83 при слиянии станет V86), прод v3.50.0 — только чтение.
Код: `backend/src/main/java/com/maxsolch/shop/ai/**` (≈2300 строк, 4 тестовых класса; тестов на `AiJobs`, лимит месяца и `AdminAiController` нет).

## 1. Что модуль уже умеет

**API** (`/api/admin/ai`, `@RequiredAdmin`, любой админ):
- `POST /jobs` — тело `Ask {feature, prompt, effort low|medium|high, researchItems 0..10}`; сразу отвечает `RUNNING` + id.
- `GET /jobs/{id}` — `RUNNING`, либо `DONE` с `Answer {text, model, costMicroUsd, tokens, modelCalls, searches, pages, repaired, ms}`; упавшая задача при опросе бросает свою ошибку.
- `GET /status` — есть ли ключ, имя модели, провайдеры поиска (включён / отдыхает), расход за месяц: итого, лимит, строки «вид × провайдер × результат» (вызовы, деньги, токены).
- `POST /search-test` — один запрос через цепочку поиска (проверка провайдеров).

**Разговор (`AiAgent`)**: одна задача = промпт от фронтенда (билдеры те же, что для копирования) → до 24 ходов модели с инструментами `search` и `open_page`. Бюджет держит код, не промпт: 3 поиска и 4 страницы на товар (`researchItems` × 3 / × 4). Бюджет исчерпан или модель попросила сверх него — следующий ход принудительно без инструментов. Если промпт просит блок json и в ответе он не парсится — один ход-починка (effort low, без инструментов). Лимит месяца проверяется перед КАЖДЫМ вызовом модели.

**Модель (`MiniMaxChat`)**: Anthropic-совместимый `/v1/messages`, таймаут 180 с на запрос, 1 повтор на сеть/502–504, 1 повтор через 3 с на 429/529. Цены из `app.ai.model.*` (micro-USD за 1 млн токенов: вход 150 000, кэш 15 000, выход 600 000), округление вверх.

**Поиск (`WebSearch`)**: SearXNG (бесплатно) → Serper ($0,001). Следующий спрашивается, только если предыдущий упал или вернул пусто. Упавший «отдыхает» 10 минут (кэш `aiSearchCooldown`); если отдыхают все — спрашиваются отдыхающие. Страницы (`WebPages`): своя загрузка с запретом внутренних адресов на каждом редиректе, при 403/429/JS-заглушке — r.jina.ai.

**Журнал `ai_usage` (V83)** — строка на каждый внешний вызов, только добавление:
`id, created_at, feature (VARCHAR 32), kind (MODEL|SEARCH|PAGE), provider (до 64: модель / searxng / serper / direct / jina), result (OK|EMPTY|FAILED), input_tokens, cached_tokens, output_tokens, cost_micro_usd, duration_ms, note (до 255)`. Индексы: `created_at`; `(kind, provider, created_at)`. Запись идёт вне бизнес-транзакции, сбой записи глотается (в лог).

**Лимит**: `AI_MONTH_LIMIT_CENTS` (по умолчанию 1000 = $10, 0 = без лимита), календарный месяц по поясу магазина (`ShopZone`), сумма всего журнала. Превышение даёт 409 `AI_MONTH_LIMIT` с суммами.

**Ошибки** (`AiError`): NOT_CONFIGURED, MONTH_LIMIT, MODEL_FAILED, JOB_NOT_FOUND, BUSY (429 + Retry-After 60), BAD_REQUEST.

## 2. Что модуль НЕ знает

| Вопрос | Сейчас |
|---|---|
| Кто запустил | Не знает. `Ask` не несёт admin id, `AiJobs.start` не читает `CurrentActor`, в `ai_usage` нет колонки админа. Запись в аудит (`AdminAuditService.record`) не делается. |
| Ради чего (товар / поставка / перевод) | Не знает. Есть только строка `feature`; связи с `product_id` / `supply_id` нет. |
| Сколько стоила ЗАДАЧА | Только в памяти внутри `Answer`. Строки журнала без `job_id`, так что «сколько ушло на этот товар» из базы не собрать (по времени ненадёжно при 3 параллельных задачах). |
| Принят ли результат | Не знает. Админка парсит ответ и сама решает, что применить; обратной связи в бэкенд нет, доли принятых правок нет. |
| Что было в промпте и ответе | Нигде не хранится, кроме часового кэша. Разбор «почему ИИ ошибся» через час невозможен. |
| Сколько стоил бы запуск | Оценки до старта нет. |

Побочная находка: `Ask.feature` проходит проверку `[a-z0-9-]{1,40}`, а колонка `feature` — 32 символа. Имя длиннее 32 в строгом режиме MySQL не запишется, а `save()` глотает ошибку: деньги потрачены, строки в журнале нет, лимит занижается. Выровнять и закрыть список функций перечислением.

## 3. Чего не хватает для целостной системы

### 3.1 Хранение задач (главное)
Сейчас `AiJobs` держит задачу в кэше Spring (`aiJobs`, 500 шт., 1 час), исполнение идёт в пуле `Workers.pool("ai", 3 потока, очередь 10)`. Последствия:
- **Рестарт / выкатка** (деплой поднимает копию и гасит старый контейнер): идущие задачи пропадают без следа. Админ видит «задача не найдена», деньги за уже сделанные вызовы потрачены (в журнале они есть, ответа нет). Дожидаться окончания при остановке нельзя: у задачи до 24 ходов по 180 с.
- **Закрытая вкладка / телефон уснул**: задача дойдёт до конца, но результат лежит только в кэше, а id знает только вкладка. Через час результат исчезает.
- **Второй экземпляр** бэкенда не видит чужие задачи (кэш у каждого свой), а при выкатке без даунтайма два экземпляра живут одновременно.
- Очередь: 11-й запрос получает «ИИ занят»; пакет на 50 товаров упрётся сразу.

Нужно: таблица `ai_jobs` (id, feature, статус QUEUED / RUNNING / DONE / FAILED / CANCELED, admin_id, объект, prompt, effort, research_items, answer, ошибка, стоимость, токены, поиски/страницы, created / started / finished / heartbeat). Исполнитель берёт задачи из БД под замком (`DbLocks` или `SELECT ... FOR UPDATE SKIP LOCKED`, не `ConcurrentHashMap`). Зависшие `RUNNING` без heartbeat помечаются как прерванные рестартом и могут быть перезапущены. Результат живёт, пока админ его не применил или не отклонил (дни, а не час).

### 3.2 История запусков
Нужен список «кто, когда, что, чем кончилось, сколько стоило, принят ли» с фильтрами (функция, админ, объект, статус, период): таблица `ai_jobs` плюс хранение промпта и ответа (чистка через 30–90 дней; лимит промпта 200 000 символов уже есть). Журнал `ai_usage` остаётся детальным по вызовам и получает `job_id`.

### 3.3 Привязка к админу и объекту
`CurrentActor` читать в `app` на старте. В фоновом потоке контекста безопасности нет, поэтому id нужно взять до `pool.execute` и положить в задачу. Поля: `admin_id`, `subject_type` (product / supply / translation-batch), `subject_id`. Запись в аудит «запустил ИИ для товара N» — через `AdminAuditService.record` (в `app`, не в контроллере). Права: сейчас любой админ; настройки и лимиты должны быть `@RequiredSuperAdmin`, расходы по другим админам видит только владелец.

### 3.4 Пакетные задачи на много товаров
Замер: «6 товаров в одном запросе» — провал (61 поиск, ответа нет), рабочий режим — 1 товар на запрос. Значит пакет = родитель + N дочерних задач (1 товар = 1 задача), общий прогресс «12 из 30», общий бюджет денег, пауза при лимите, продолжение после рестарта. Параллелизм ограничен не только 3 потоками: Google CSE в SearXNG банит после ~70 запросов за 5 минут, нужен общий темп поиска, а не только число потоков. Очередь на сотню товаров живёт в БД, а не в «10 в очереди».

### 3.5 Отмена и повтор
Отмены нет вообще: пока задача идёт, остановить её нельзя (ходы продолжают тратить деньги). Нужно: флаг `cancel_requested` в БД, проверка между ходами в `AiAgent` (текущий ход до 180 с не прерываем, следующий не начинаем); у пакета «остановить всё». Повтор: новая задача с теми же параметрами (`retry_of`) и возможностью поднять effort; защита от двойного клика (одна активная задача на `(feature, объект)`). Общего потолка времени задачи нет (теоретически 24 × 180 с) — нужен дедлайн задачи.

### 3.6 Настройки в базе вместо env
Сейчас всё в `application.yml` / env, правка = перезапуск. В архитектуре уже есть модуль `settings` (`SettingsContribution`, `SettingDefinition`: INT / STRING / SELECT, группы, снимок 60 с со сбросом при сохранении). Секреты (`AI_MINIMAX_KEY`, `AI_SERPER_KEY`, URL SearXNG) остаются в `.env` и не отдаются API; в базу идут только бизнес-параметры. Кандидаты для `SettingsContribution` модуля `ai` (дефолты = текущее поведение):
- ИИ вкл/выкл целиком и по функциям (карточки, поставка, переводы);
- модель и effort по функциям (карточки medium, накладные low), бюджет поисков и страниц на товар (сейчас константы 3 / 4), максимум ходов, дедлайн задачи;
- лимиты: месяц, день, на админа в день, на задачу, на пакет; порог предупреждения (80 %);
- цены модели и Serper (сейчас `app.ai.model.*`), курс USD в UAH для показа в гривнах;
- порядок поиска и вкл/выкл провайдеров;
- срок хранения промптов и ответов.
Лимит месяца переезжает из env в настройки (env остаётся значением по умолчанию).

### 3.7 Метрики: чего нет в эндпоинтах
Есть только `GET /status` — сумма с начала месяца по `(kind, provider, result)`. Нужны запросы (в `infra/*Queries`, там JDBC допустим):
- по дням и неделям: деньги, вызовы, токены, поиски, ошибки (для графика);
- по функциям, провайдерам, моделям;
- по админам (нужна колонка `admin_id`);
- **стоимость результата**: ₴ на карточку / накладную / перевод = сумма по `job_id` / число принятых результатов;
- **доля принятых правок**: нужна обратная связь от фронтенда, после «Применить» админка шлёт `POST /jobs/{id}/outcome` (принято / отклонено / исправлено по полям). Без неё качество не измерить: бенч 88 % сравнивал с ChatGPT, а не с решениями админа;
- качество поиска: доля EMPTY / FAILED по провайдерам, расход Serper относительно бесплатных 2500, время ответа (p50 / p95 по `duration_ms`);
- доля починок JSON (`repaired`), отмен, падений от рестарта;
- прогноз: «при текущем темпе лимит закончится N-го числа».

Деньги в модуле — `long` в micro-USD, в UI нужны гривны: один пересчёт на бэкенде по курсу из настроек, а не `double` во фронтенде. Правило «деньги = long minor» относится к гривневой стороне; micro-USD оставить явным, подписанным исключением модуля.

### 3.8 Уведомления о лимите
Нет совсем: админ узнаёт о лимите только по ошибке 409. Нужно: пороги 80 % и 100 % — одно событие на порог за период (флаг в БД, чтобы не слать повторно после рестарта) → web push через `AdminPushService` / `SellerChannel` по схеме «модуль публикует событие, `AiNotifier` в `app` слушает через `@OnCommitted`». Ещё события: поисковик начал блокировать (много EMPTY подряд), ключ MiniMax не принят (401), баланс на исходе.

### 3.9 Оценка стоимости до запуска
Нет. Данные для неё есть: замер (карточка medium ≈ 0,20 ₴, накладная low ≈ 0,08 ₴) и собственная история из `ai_usage`. Нужен `POST /estimate {feature, items}` → диапазон (p50–p90 из журнала по функции, пока истории мало — константы замера) и «хватит ли остатка лимита»; для пакета — «примерно N ₴, M минут».

### 3.10 Прочие пробелы
- **Картинки на входе**: `Ask` и `ChatModel` только текстовые. Накладную Taobao в замере читали со скриншотов (6/6 строк), а в бэкенде способа передать изображение нет. Для ИИ-поставки это обязательная доработка (загрузка скринов, лимит размера, не хранить дольше задачи).
- **Гонка лимита**: проверка до вызова + запись после — три параллельные задачи могут вместе перешагнуть лимит (на копейки сейчас, заметнее при пакетах). Решение: резерв в БД или проверка на уровне задачи/пакета.
- `/status` считает сумму и сводку по журналу без ограничений; при росте таблицы нужны дневные агрегаты или чистка старых строк со сохранением свёрток.
- Нет аварийного выключателя (ИИ льёт деньги или глючит) без перезапуска — это настройка из 3.6.
- Тестов нет на `AiJobs` (очередь, BUSY, ошибки), лимит месяца, контроллер.

## 4. Ограничения архитектуры (учесть при доработке)
Источник: `docs/ARCHITECTURE.md`; ArchUnit проверяет весь код без исключений.
1. **Модуль `ai`**: слои `api / app / domain / infra`. Соседи (настройки, аудит, push, staff для имён админов) — только по разрешённой цепочке зависимостей; новые связи через порты, не через чужие репозитории.
2. **Файл ≤ 400 строк, метод ≤ 80** (`ClassSizeTest`, `MethodSizeTest`). `AiAgent` 177, `MiniMaxChat` 164 — запас есть, но очередь, пакеты, метрики и лимиты — отдельные классы (`AiJobStore`, `AiBatches`, `AiUsageQueries`, `AiLimits`, `AiNotifier`), `AiJobs` не раздувать.
3. **Деньги** — `long`; здесь micro-USD, в UI гривны по курсу из настроек (один способ округления).
4. **Время** — только `Clock` + `ShopZone`; `Instant.now()`, `System.currentTimeMillis`, `ZoneId.of` запрещены. Границы дня и месяца для лимитов — по `ShopZone`, как `monthStart()`.
5. **Кэш** — только `CacheSpec` + `CacheConfig.require`. Кэш подходит для снимков и «отдыха» поиска; задачи в нём держать нельзя, источник правды — БД.
6. **Блокировки только в БД** (`DbLocks`, `SELECT ... FOR UPDATE`); `synchronized` и `ConcurrentHashMap` как замок запрещены. Один пакет — один исполнитель; одна активная задача на объект; сброс зависших задач при старте.
7. **Потоки** — только `platform.jobs.Workers`; плановые чистки и добивка — `app/*Jobs` + `@SchedulerLock`.
8. **Внешние HTTP** — через `platform.http`, таймауты обязательны, ретраи только безопасные (запрос к модели стоит денег: повторы допустимы только на ошибки до начала генерации, как сейчас).
9. **Конфиг** — `@ConfigurationProperties` + `@Validated`, `@Value` запрещён; редактируемое из админки — `SettingsContribution`; секреты остаются в `.env`.
10. **События** — `DomainEvents.publish` и слушатели `@OnCommitted` (пороги лимита, завершение пакета).
11. **Аудит** — в `app` через `AdminAuditService.record`, актор — `CurrentActor`; в фоновом потоке актора нет, id несётся в задаче.
12. **Права** — только аннотации: `@RequiredAdmin` на запуск, `@RequiredSuperAdmin` на настройки, лимиты и чужие расходы.
13. **Миграции** — только добавление, совместимость с прошлым бэкендом при откате (rollback.sh откатывает образы, не базу). V83 станет V86, дальше V87+; ветка Новой почты тоже ждёт V87+, номера согласовать.
14. **Тексты ошибок** — `error.ai.<NAME>` в i18n-бандлах (админка русская, но ключи обязательны).
15. **Выкатка без даунтайма** (копия `_next`): два экземпляра живут одновременно, ещё один довод хранить задачи и замки в БД; исполнитель обязан корректно отдавать задачи, когда старый экземпляр гасят.

## 5. Минимальный состав доработки бэкенда (предложение)
1. Миграции: `ai_jobs`, связь пакета (`parent_id` / `ai_batches`), колонки `job_id`, `admin_id`, `subject_*` в `ai_usage`, флаги порогов (`ai_alerts`).
2. `AiJobs` → очередь в БД + исполнитель + отмена + повтор + сброс зависших; `GET /jobs` (история), `POST /jobs/{id}/cancel | retry | outcome`, `POST /batches`.
3. `SettingsContribution` модуля `ai` + `AiLimits` (месяц / день / админ / задача / пакет, резерв).
4. `AiUsageQueries` + `GET /metrics?from&to&groupBy=day|feature|provider|admin`, `POST /estimate`.
5. `AiNotifier` (пороги лимита, блокировка поиска, ошибка ключа).
6. Вход с изображениями для функции «поставка».
7. Тесты: очередь и рестарт, лимиты, отмена, расчёт метрик; ArchUnit остаётся зелёным.
