# 03. Технический разбор дизайна (бэкенд + фронт)

Роль: технический критик. Проверено: `02-design.md` против `backend/.../ai/**` (ветка feat/ai-assist, 1815 строк, V83), `00-backend.md`, фронта прод v3.50.0 (`frontend-admin/features/{cards,supply,translation,analytics,staff}`, `shell/`), `ARCHITECTURE*.md`, `deploy.sh`, `DbLocks`, `Workers`, `CardMeta`.
Формат: проблема → почему плохо → предложение. Важность: **blocker** (без решения дизайн не построить или он будет врать), **major** (построить можно, но дорого или с дырой), **minor**.

Общий вердикт: дизайн хороший как поведение, но опирается на три вещи, которых в коде нет и которые не мелкие: (1) очередь задач в БД, переживающая выкатку, (2) бэкенд, который знает, что и для кого считает (сейчас он получает от фронта голый промпт), (3) обратная связь «принят / исправлен» от фронта. Без них половина экранов (центр задач, пакет с паузой, «ждёт проверки», метрики «принято без правок», «зря потрачено») показывает выдуманные данные.

## Blocker

### B1. Задачи живут в кэше процесса, а выкатка идёт с двумя копиями бэкенда
- **Факт.** `AiJobs`: кэш `aiJobs` (500 шт., 1 час), пул 3 потока + очередь 10. `deploy.sh` поднимает `<имя>_next`, затем `docker stop -t 35` старого. Спринг ждёт до 30 с, а задача идёт до 24 ходов × 180 с.
- **Почему плохо.** Каждый релиз убивает все идущие задачи; второй экземпляр не видит задач первого (в течение выкатки опрос с телефона попадает то в одну копию, то в другую: «задача не найдена» на живой задаче). Для пакета на 40 товаров (≈ 10–15 минут при 3 параллельных) выкатка в это окно почти гарантирована. Статус «Прервана перезапуском» из дизайна без перезапуска задач просто признание потери денег.
- **Предложение.** Таблица `ai_jobs` — единственный источник правды. Исполнитель забирает задачу одним `UPDATE ... SET status='RUNNING', owner=:instance, heartbeat=now WHERE id=(SELECT ... WHERE status='QUEUED' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED)` (MySQL 8.4 это умеет). Heartbeat раз в 15 с; «зависшей» считается RUNNING с heartbeat старше 60 с (не раньше: у старой копии идёт мирное доживание). При SIGTERM: перестать забирать новые, текущей дать закончить текущий ход (≤ 180 с не успеть за 35 с) и вернуть задачу в QUEUED со счётчиком `attempt` (один авто-перезапуск, потом ABORTED). Потерянные деньги первой попытки остаются в `ai_usage`, в задаче видны как «попытка 1: прервана, ушло X». Диалог посреди задачи не сохранять, перезапуск с начала: это в разы проще, потеря копейки. Пул `Workers.pool` с лимитом 3 остаётся, но лимит параллелизма должен быть общим на все копии: считать RUNNING в БД, а не потоки процесса (иначе во время выкатки одновременно 6).
- **Трудоёмкость:** L (таблица, исполнитель, heartbeat, reaper по `@SchedulerLock`, graceful-стоп, тесты на рестарт и две копии).

### B2. Пакет не может жить на фронте, а промпт собирает фронт
- **Факт.** `POST /jobs` принимает `Ask{feature, prompt, effort, researchItems}`. Промпт строит `buildCardPrompt` (22 КБ текста + схема категорий + глоссарий) в браузере.
- **Почему плохо.**
  1. Пакет на 40 товаров «закрыл экран, продолжу в фоне» работает, только если все 40 промптов собраны и отправлены в момент старта (≈ 40 × 25–30 КБ ≈ 1 МБ тела). Повтор неудачных «Повторить (8)» через день делается из сохранённых промптов, схема категорий за это время могла измениться, а `assignCardIds` зависит от набора товаров.
  2. Бюджет поиска (`researchItems` × 3/× 4), `effort` и `feature` приходят от клиента: любой админ с devtools снимает ограничения; «оценка цены до запуска» невозможна, потому что бэкенд не знает, сколько товаров в промпте.
  3. Лимит и оценка по сути несут слова клиента.
- **Предложение.** Контракт задачи: `POST /jobs {feature, subjects:[{type,id}], mode(quick|normal|thorough), prompt, files?}`; бэкенд сам выводит `researchItems = subjects.length`, `effort` из режима и настроек, `feature` — enum. Промпт остаётся от фронта (билдеры и парсеры в одном месте, не дублировать в Java), но сохраняется в задаче вместе с `prompt_version` (константа в билдере) и `subjects`, чтобы повтор не перестраивал его. Для пакета фронт отправляет N дочерних задач одним `POST /batches` (1 транзакция, лимит размера тела поднять на этом пути до 4 МБ). Оценку считает `POST /estimate {feature, subjects, mode}` по `ai_usage`-истории.
- **Трудоёмкость:** M (контракт, валидация, батч-эндпоинт).

### B3. «Пусто / Ответ не читается / Готово» определяет парсер на фронте, а бэкенд этого не знает
- **Факт.** `reviewAnswer`/`check.ts` — чистый TS во фронте. `AiAgent` проверяет только «JSON читается» (`jsonProblem`) и чинит один раз.
- **Почему плохо.** Итог пакета «32 готово · 5 пусто · 3 ошибки», бейдж «ждёт проверки», правило «3 ошибки подряд → ручной путь», метрики «зря потрачено» и «принято без правок» требуют знать результат разбора по всем задачам, в том числе ни разу не открытым. Бэкенд вечно будет считать их «Готово».
- **Предложение.** Два уровня. Бэкенд: структурная проверка на выходе из `AiAgent` (JSON парсится, есть блок для каждого ожидаемого `subject`, хотя бы одно непустое поле) → статусы DONE / EMPTY / BAD_ANSWER. Фронт: смысловой разбор и «красное/сомнительное» при открытии ревью и `POST /jobs/{id}/outcome {applied, rejected, edited:[field], ignoredLocked}` один раз, идемпотентно (ключ job+version). В метриках явно разделить «принято из N проверенных» и «не открыто».
- **Трудоёмкость:** M.

### B4. Картинки для «Прочитать с ИИ»: нужны хранение, PDF→PNG и сквозной путь, дизайн это ломает
- **Факт.** `ChatModel.Block` = Text / ToolCall / ToolResult / Other, картинок нет. Multipart ограничен 15 МБ. Дизайн: «файлы не хранятся».
- **Почему плохо.** При хранении в БД-очереди (B1) повтор, авто-перезапуск после выкатки и «Повторить неудачные» требуют, чтобы файлы лежали, пока жива задача. «Не хранятся» + перезапуск несовместимы. Плюс: PDF накладной надо рендерить в PNG на сервере (в проекте нет такой библиотеки, значит новая зависимость и риск OOM на больших PDF), 3–10 скринов телефона по 3–8 МБ в base64 (+33 %) легко превышают лимиты шлюза Caddy и 64 МБ тела провайдера.
- **Предложение.** Загрузка отдельно: `POST /ai/files` (MinIO-бакет с TTL 7 дней, лимит 10 МБ на файл, 10 файлов, только JPEG/PNG/WEBP/PDF), в задачу идёт список `fileId`. Серверный даунскейл до ~1600 px по длинной стороне перед отправкой модели (экономит токены). PDF: ограничить 10 страниц, рендер в отдельном шаге под лимитом памяти. После завершения и применения файлы удаляются по `@SchedulerLock`-чистке; в дизайне заменить «файлы не хранятся» на «хранятся до 7 дней, потом удаляются». Пока этого нет, кнопка остаётся ручной (как в дизайне), но это надо писать в этап 1 честно: поставка этап 2.
- **Трудоёмкость:** L (хранилище, рендер PDF, мультимодальный запрос, лимиты, чистка).

## Major

### M1. Лимиты «замки только в БД»: гонка резервирования расхода
- **Факт.** `ensureWithinLimit()` читает `SUM(cost)` перед каждым ходом, запись строки после. Три параллельных потока (и две копии при выкатке) перешагивают лимит; запись `save()` ещё и глотает ошибки (колонка `feature` VARCHAR(32), валидатор пропускает 40 символов).
- **Почему плохо.** Дизайн обещает лимиты: месяц, день, на админа, на пакет, «пауза при исчерпании». Сейчас они проверяются «на глаз» и без атомарности; при пакетах перелёт заметен.
- **Предложение.** Резерв: при взятии задачи в работу в одной транзакции `INSERT ai_reserve(job_id, micro_usd)` по оценке p90, проверка `SUM(spent)+SUM(active reserves) <= limit` под `DbLocks.lockWaiting("ai-limit")` (короткий замок, секунды). По завершении резерв заменяется фактом. Дневной/по-админный лимит считаются тем же запросом с `WHERE admin_id`/`WHERE created_at>=:dayStart` (границы по `ShopZone`). Поменять `feature` на enum, длину VARCHAR привести к проверке, а `save()` при сбое писать в лог с суммой и повышать счётчик «потерянных строк» (иначе лимит занижается молча).
- **Трудоёмкость:** M.

### M2. Опрос с телефона: живая задача, спящий экран, и сколько запросов
- **Факт.** Есть `refetchInterval` (30 с–2 мин) в бейджах меню и `useQuery` без фоновой работы; WebSocket разрешён только из `shell/realtime.ts`; интервал фонового опроса на iOS в PWA замораживается при сне.
- **Почему плохо.** Чип ✦ с «идут N» и тост «готово» требуют частого опроса (3–5 с) только пока что-то идёт. На телефоне после сна опрос не восстановится до возвращения на экран, тост придёт с опозданием; а «Прервана» для пользователя выглядит как «потеряно».
- **Предложение.** Один лёгкий эндпоинт `GET /ai/jobs/active?since=<etag>` (счётчики по статусам + изменения), `refetchInterval` условный: 4 с при `running>0 && document.visibilityState==='visible'`, иначе 60 с; обновлять по `visibilitychange`/`online`. В шапке чип питается от этого запроса, а не от списка. Если нужен мгновенный тост — тема STOMP `/topic/admin/ai` из `realtime.ts` (транспорт уже есть, правило ws-only-from-realtime соблюдается), но это опциональный этап 2; polling как база. Web push «готово группой» (вопрос 4 владельцу) стоит вынести в основу для пакетов: с телефона во сне ничего другого не сработает.
- **Трудоёмкость:** S (polling), M (STOMP+push).

### M3. Пакеты на десятки товаров: темп поиска, а не число потоков
- **Факт.** Замер: «6 товаров в одном запросе» провал; 1 товар = 1 задача. SearXNG→Google CSE банит после ~70 запросов за 5 минут; 3 потока × 3 поиска/товар ≈ 9 запросов на «тройку товаров» за ~1 минуту → ~45/5 минут на каждый пакет, а запущенных пакетов может быть два.
- **Почему плохо.** Пакет 40 товаров «молча» пройдёт на SearXNG, в середине начнутся EMPTY, провайдер уйдёт «отдыхать» на 10 минут (кэш в памяти, у каждой копии своё), затем пойдёт Serper за деньги, и «0,2 ₴» вдвое-втрое вырастет без предупреждения.
- **Предложение.** Общий лимитер темпа поиска в БД (счётчик «поисков за последние 5 минут» из `ai_usage`, потолок настройкой, например 40), задачи ждут QUEUED, а не падают. «Отдых» провайдера хранить в БД (таблица или `ai_usage`-запрос), а не в кэше. В оценке пакета показывать сценарий «если уйдёт на Serper»: потолок = число запросов × $0,001. Параллелизм пакета (1–3) — настройка; для пакета ≥ 20 товаров ставить 2, чтобы не сжечь поиск.
- **Трудоёмкость:** M.

### M4. Нет отмены, повтора и защиты от двойного клика
- **Факт.** Отмены нет совсем, «одна активная задача на объект» не реализована.
- **Почему плохо.** Кнопка «Остановить», «Остановить всё немедленно», «Повторить», «уже идёт: запустила Анна» из дизайна всё это требует отдельных механизмов. Два админа жмут одновременно: оба получат платный запуск. Двойной тап на телефоне то же самое.
- **Предложение.** Таблица: `UNIQUE (subject_type, subject_id, active_key)` где `active_key = id` для QUEUED/RUNNING и NULL после завершения (уникальный индекс по `NULL` в MySQL допускает дубли, это как раз нужно) или `active=1` и частичная имитация через вычисляемую колонку; вставка дубля даёт 409 с данными активной задачи (`startedBy`, `startedAt`) → экран «уже идёт». На фронте идемпотентный ключ мутации (в `useApiMutation` он уже есть) + блокировка кнопки. Отмена: `cancel_requested` в БД, проверка между ходами в `AiAgent` (текущий ход ≤ 180 с не прерывать). «Остановить всё» = глобальный флаг в настройках + массовая отмена QUEUED + запрос cancel для RUNNING. Повтор = новая задача `retry_of`, право: свой или владелец.
- **Трудоёмкость:** M.

### M5. Хранение ответа, дифф и «ревью по дням»: дифф нельзя хранить, он зависит от состояния карточки
- **Факт.** Ревью строится на фронте из текста ответа и текущего `CardItem`. `CardMeta` хранит `last` до/после только после применения; флаг `edited` ставится только на полях, которые уже трогал ИИ.
- **Почему плохо.** Дизайн: ревью может быть открыто через час/день на другом телефоне. «Конфликт: карточку правил Иван» требует знать, что карточка изменилась после старта. Группа «Правил человек, заблокировано» опирается на то, чего нет: поле, заполненное руками до первого ИИ-импорта, в `card_meta` не помечено (пометка `edited` появляется только на уже ИИ-изменённых полях).
- **Предложение.** В задачу сохранять `subject_version` (`updated_at`/hash карточки на момент старта) и при открытии ревью сравнивать с текущим: изменились поля после старта → блокировать именно их (дизайн прав). Группу «Правил человек» определять так: значение не пусто И (нет в `card_meta.last` ИЛИ `edited=true`); текст у дизайна честно поправить: «заполнено не ИИ». Дифф считать на фронте при открытии (чистая функция, не хранить), хранить только сырой ответ и `outcome`. Хранить ответ и промпт 60 дней в `ai_jobs.answer/prompt` (MEDIUMTEXT) отдельной таблицей-«телом» (`ai_job_bodies`), чтобы список и метрики не тащили мегабайты и чистка по сроку шла по одной таблице.
- **Трудоёмкость:** M.

### M6. Метрики на агрегатах: журнал по вызовам не переживёт запросы дашборда
- **Факт.** `ai_usage` — 1 строка на вызов, индексы `(created_at)` и `(kind, provider, created_at)`. Нет `job_id`, `admin_id`, `subject_*`. `summarySince` делает `GROUP BY` по всему месяцу на каждый `GET /status`.
- **Почему плохо.** Оценка объёма: карточка ≈ 6–10 вызовов (ходы, поиски, страницы), 200 карточек в месяц ≈ 2 тыс. строк, пакеты и перевод ≈ 5–10 тыс./мес: вовсе не страшно (до ~100 тыс. в год). Проблема не объём, а срезы: «по админам», «₴ на результат», «топ исправляемых полей», «зря потрачено» требуют колонок, которых нет, и сумм по задаче.
- **Предложение.** Миграции: `ai_usage` + `job_id BIGINT NULL`, `admin_id BIGINT NULL`, индекс `(job_id)` и `(feature, created_at)`; итоги по задаче денормализовать в `ai_jobs` (cost, tokens, searches, pages, duration) в момент завершения, тогда «₴ на результат» = `SUM(cost)/COUNT(outcome=APPLIED)` по `ai_jobs`, без обращения к `ai_usage`. Дашборд: графики по дням из `ai_jobs`, детальный разрез провайдеров из `ai_usage` с обязательным `created_at >=` диапазон. Свёртки по дням (`ai_usage_day`) не нужны до ≈ 1 млн строк; вместо этого чистка `ai_usage` старше 400 дней по `@SchedulerLock` и запись месячного итога. «Топ исправляемых полей»: хранить в `ai_jobs.outcome_json` поле-флаги (не в отдельной таблице).
- **Трудоёмкость:** M (миграции + запросы `AiUsageQueries` в `infra/*Queries`).

### M7. Деньги: микро-USD → гривны, фракции и курс
- **Факт.** Бэкенд хранит `long` micro-USD, дизайн показывает «0,2 ₴», «0,08 ₴»; в `ARCHITECTURE-FRONT` запрещены `/100`, `toFixed` для денег, `money()` работает в minor.
- **Почему плохо.** Строка журнала часто стоит < 1 копейки; сумма округлённых строк ≠ округлённая сумма. Пересчёт по текущему курсу переписывает историю (расход прошлого месяца «поплывёт» при смене курса в настройках), «сэкономлено» (константа × число) смешивается с фактом.
- **Предложение.** Хранить USD в micro-USD (факт, неизменно) и курс, действовавший на момент завершения задачи, в `ai_jobs.rate_milli` (UAH за USD ×1000). В API отдавать и `costMicroUsd`, и `costMinor` (копейки), округляя один раз на агрегате на бэкенде. Фронт показывает `money(costMinor)`; для сумм меньше копейки есть формат «< 1 коп.» (в дизайне не описан). Лимиты в настройках в гривнах (long minor), пересчёт в USD на бэкенде по курсу, который владелец ведёт сам (раз в месяц). «Сэкономлено» подписать «оценка» (уже есть) и вынести константы в настройки, не в код.
- **Трудоёмкость:** S.

### M8. Права: «владелец / обычный админ» в коде это SUPER_ADMIN / ADMIN / RequiresFinance
- **Факт.** Роли `ADMIN` и `SUPER_ADMIN`; отдельно `RequiresFinance`/`FinanceGuard`. Контроллер `AdminAiController` сейчас `@RequiredAdmin` на весь класс, `/status` и `/search-test` доступны любому админу.
- **Почему плохо.** Дизайн: деньги и промпты только владельцу, настройки только владельцу, «видеть чужие задачи». Ограничение «без сумм» на фронте (скрыть в UI) без бэкенда не защита: JSON уже содержит `costMicroUsd`.
- **Предложение.** Разделить DTO: `JobView` (без денег, промпта) и `JobDetail` (владелец); решать на бэкенде по роли. Определить «владелец» = `SUPER_ADMIN` (проверить, совпадает ли с `RequiresFinance`: расход на ИИ — финансовая информация; если финансы отдельная роль, согласовать). `GET /status`, `/search-test`, `/metrics`, настройки: `@RequiredSuperAdmin`. Админ видит «осталось/не хватит» булевым полем `canRun`. Аудит `AdminAuditService.record` в `app`, актор берётся до `pool.execute`.
- **Трудоёмкость:** S–M.

### M9. Оценка цены до запуска
- **Факт.** Эндпоинта нет; замеры 0,20 ₴ (карточка, medium) и 0,08 ₴ (накладная) на 1–3 штуках; разброс 30–60 с.
- **Почему плохо.** «≈ 0,2 ₴» в кнопке будет константой; «тщательно» стоит дороже в разы (24 хода, больше страниц), у «пустых» карточек поиск тратит бюджет целиком, у популярных быстро. Подтверждение «только если дороже 2 ₴» тогда срабатывает по ложной оценке.
- **Предложение.** `POST /estimate`: `p50/p90` по `ai_jobs` последних 30 дней по `(feature, mode)` с минимум 10 завершёнными, иначе константы замера × коэффициент режима; «хватит ли» = `limitLeft - reserved - estimate*N`. В подписи кнопки всегда p50, в окне подтверждения диапазон p50–p90. Результат кэшировать на 60 с (`CacheSpec`).
- **Трудоёмкость:** S–M.

### M10. Настройки: база вместо env, но с аварийной кнопкой, которая должна работать без кэша
- **Факт.** Есть `SettingsContribution` (снимок 60 с, сброс при сохранении), секреты в `.env`. «Остановить всё немедленно».
- **Почему плохо.** Снимок на 60 с в каждой копии: «стоп» срабатывает на второй копии до минуты (при выкатке две копии). Выключатель должен быть быстрым.
- **Предложение.** Проверку `enabled` и `killSwitch` делать из БД без снимка на старте каждой задачи и между ходами (один `SELECT` по ключу, это дёшево), остальные настройки через снимок. Для лимитов и функций использовать `SettingsContribution` с группой «ИИ» (`SettingGroup`); «Модель и ключи только для чтения» подтверждено архитектурой (секреты не отдавать), но API должен отдавать «ключ задан / нет» и результат `status`, не сам ключ.
- **Трудоёмкость:** M.

## Minor

### N1. Экран ревью на 375 px и число состояний
- **Факт.** Дизайн: счётчик «Принять 9 из 14», 4 группы, у каждого поля уверенность, источник, причина, замок, футер с 5 действиями в «⋯».
- **Почему плохо.** На 375 px это стена: у поля 4 вспомогательных элемента (бейдж уверенности, источник, причина, чекбокс) плюс 4 группы. Состояний входа 6, статусов 5, экранов-состояний в `09-states` 11, плюс режимы «владелец/админ»: тестов и ветвей (в `use-card-completion.ts` уже ~20 `useState` в одном хуке, лимит файла 400 строк, компонента 200) будет слишком много. Риск превышения ESLint-лимитов (`complexity 15`) в `ui/`.
- **Предложение.** Свернуть состояния в одну машину состояний (чистая `model/job-state.ts` с таблицей переходов + unit-тесты, UI только рисует), не `useState` на каждое. На телефоне ревью: группа «Заменит/Сомнительно» свёрнута по умолчанию, у поля одна строка + раскрытие (источник/причина внутри). Состояний-экранов оставить в макетах минимум и считать остальные вариантами одного компонента (баннер + кнопка).
- **Трудоёмкость:** S (при правильной модели).

### N2. Межфичевые зависимости фронта и размеры файлов
- **Факт.** Правила: `app → features`, «одна задача — один способ», файлы ≤ 400 строк. Новая фича `ai` должна называться как модуль бэкенда; `cards`, `supply`, `translation` обращаются к ней, шапка (`shell/`) показывает чип.
- **Предложение.** `features/ai/` (api, queries, model: состояние задачи, оценка, форматирование; ui: `AiEntryButton`, `AiJobSheet`, `AiTaskCenter`, `AiSettings`, `AiMetrics`) с публичным `index.ts`; фичи cards/supply/translation импортируют только оттуда, а промпт-билдеры и парсеры остаются у своих фич и передаются как «адаптер» (`{buildPrompt, parseAnswer, subjects}`), чтобы `ai` не знал о `cards`. Этим же убирается зоопарк из трёх хуков (`use-card-completion`, `use-supply-ai`, translation) в один паттерн.
- **Трудоёмкость:** M (основной объём фронта).

### N3. Лишний уровень: «поиск недоступен (3 кнопки)» и три режима качества
- **Факт.** Дизайн: «подождать / без поиска с пометкой / вручную», режимы быстро/обычно/тщательно, настройка поиска, функции, лимиты по 5 разрезам.
- **Почему плохо.** Каждый тумблер = состояние в БД, тест и текст. «Без поиска с пометкой» это ответ без источников, по замеру модель на редком товаре галлюцинирует; ложная уверенность.
- **Предложение.** Начать с двух режимов (обычно/тщательно), «без поиска» убрать из выбора пользователя (оставить автоматикой при недоступном поиске только как «Пусто → вручную»). Лимиты этапа 1: месяц + день + на пакет; «на админа» отложить.
- **Трудоёмкость:** экономит M.

### N4. Автоповтор JSON-починки и стоимость «Пусто»
- **Факт.** `AiAgent` делает 1 ход-починку; при исчерпании 24 ходов возвращает пустой текст `""` и всё равно сжигает все ходы.
- **Предложение.** Потолок стоимости на задачу (в настройках, например 3× p50) и выход по нему как «Пусто, потрачено X»; иначе «зря потрачено» растёт без предела. Дедлайн задачи по времени (например 5 минут) в настройках.
- **Трудоёмкость:** S.

### N5. Уведомления о лимите без повторов после перезапуска
- **Факт.** Порогов 80 % / 100 % нет.
- **Предложение.** Флаг в `ai_alerts (period, threshold)` с `UNIQUE`; `DomainEvents` + `@OnCommitted` + `AdminPushService`. `INSERT IGNORE` как замок.
- **Трудоёмкость:** S.

### N6. Тесты
- **Факт.** Нет тестов на `AiJobs`, лимит, контроллер.
- **Предложение.** До переписывания очереди: характеризующие тесты (поведение BUSY, FAILED, DONE) и интеграционный тест с Testcontainers MySQL: два исполнителя одной таблицы (SKIP LOCKED), reaper, лимит-резерв. Без них B1/M1 не принять.
- **Трудоёмкость:** M.

## Порядок, который снижает риск
1. Очередь в БД + `ai_jobs` + идемпотентность + права (B1, B2, M4, M8). Без этого ничего не выкатывать.
2. Одна функция сквозь всё: «Карточка одного товара» (кнопка, чип, ревью, outcome). Цифры реального расхода начинают копиться.
3. Лимиты с резервом, оценка, настройки, kill-switch.
4. Пакет (темп поиска, пауза, повтор неудачных).
5. Переводы (текст, без картинок).
6. Метрики и виджет (данные к этому времени уже есть).
7. Поставка с картинками (B4) последней.
