## 0. Что уже известно про исходное состояние

- В ветке `feat/ai-assist` (HEAD `4bfe0115`) модуль `ai`: 841 строка в `app`, тесты только на `AiAgent`, `WebSearch`, `PageText`, адаптеры. Нет тестов на `AiJobs` и лимит месяца. Контроллер один, `AdminAiController` (`@RequiredAdmin`).

## Э1. Движок: задачи в БД, лимиты, настройки, предупреждения

Условие всех дальнейших экранов. Админам ничего не показываем, владелец видит настройки и статус, этого достаточно, чтобы прописать на проде ключи и проверить сквозь живую цепочку (поиск, модель) до появления кнопок.

**Что видит пользователь.**
- Владелец: Настройки → группа «ИИ» (блоки «Состояние», «Лимиты», «Функции», «Поиск», «Уведомления», «Дополнительно», история изменений), кнопка «Проверить поиск», строка «Бесплатных Serper использовано N из 2500». Push-предупреждения (7 событий) работают с этого релиза.
- Админ: ничего. Выключатели функций стоят в «выкл».

**Бэкенд (модуль `ai`, слои api/app/domain/infra).**
- Миграции V87–V89 (см. таблицу п. 1). `ai_jobs`: `id`, `feature`, `status` (QUEUED/RUNNING/DONE/EMPTY/BAD_ANSWER/FAILED/CANCELED), `admin_id`, `subject_type`, `subject_id`, `subject_version`, `mode`, `prompt_version`, `retry_of`, `cancel_requested`, итоги (`cost_micro_usd`, `rate_milli`, токены, поиски, страницы, модель-вызовы, `outcome`, `path` встроенный/ручной), `created_at/started_at/finished_at/heartbeat_at/deadline_at`, `locked_by`. Уникальность активной задачи по `(subject_type, subject_id)`: `active_key` как вычисляемый столбец с UNIQUE (для не-активных NULL). `ai_job_bodies`: промпт и ответ, чистка через 60 дней (`@Scheduled` + `@SchedulerLock`). `ai_reserve`: резерв расхода на запущенную задачу. `ai_alerts (period, threshold)` с UNIQUE, `INSERT IGNORE` как замок.
- Классы (новые, `AiJobs` не раздуваем):
  - `domain`: `AiFeature`, `JobStatus` + таблица допустимых переходов, `AiJob` (меняется только методами `start/finish/fail/cancel/requeue`), `AiMoney` (micro-USD → `costMinor` по курсу задачи, округление вверх, один способ), `AiLimitReached`/`AiKeyRejected`/`AiSearchDown` события.
  - `infra`: `AiJobRepository` (JPA) + `AiJobClaims` (JDBC `SELECT … FOR UPDATE SKIP LOCKED`, в `infra`, как разрешено для запросов), `AiUsageQueries` (JDBC, нужные срезы для Э3 закладываем сразу: на дни, функции, провайдеры).

  - Аудит: `AdminAuditService.record` из `AiJobs` (запуск, отмена, изменение лимита); id админа берётся до `pool.execute` и кладётся в задачу (в фоновом потоке `CurrentActor` нет).

Админу `JobView` без денег и промпта, владельцу `JobDetail`. 409 при активной задаче по тому же объекту с данными этой задачи. Идемпотентный ключ в заголовке.

## Э2. Карточка и дозаполнение — основной путь

**Что видит админ.** В окне создания/дозаполнения карточки (три входа: после создания товара, строка списка, товар поставки) акцентная кнопка «Заполнить с ИИ» с оценкой «около минуты» и рядом ссылка «Через ChatGPT вручную». Ход работы. Ревью полноэкранной страницей: группы «Проверьте / Заполнит пустое / Заменит значение / Заполнено не ИИ», счётчик «Выбрано N из M», «Применить (N)», «⋯» с ручным путём, «Повторить тщательнее» (один раз), «Отклонить». Чип ✦ в шапке (всегда виден, 320 и 375). Конфликт правок («Иван изменил в 14:20…»). Владелец дополнительно видит цены в оценке и повторе.
Включается выключателем «Карточки» (по умолчанию выкл). Ручной путь работает как сегодня при любом состоянии выключателя.

**Бэкенд.** Миграций нет. Нужное:
- Сценарий `AiCardJobs` (`app`): собирает `subjects` из `product_id`, фиксирует `subject_version` (хеш/updatedAt карточки), выбирает `effort` (medium для карточек) и бюджет поиска (3 поиска, 4 страницы на товар). Промпт приходит от фронта (билдеры остаются в `cards/model/prompt.ts`), версия промпта сохраняется.
- `AdminAiJobsController` расширяется только по существу (уже есть из Э1). Ожидается один новый эндпоинт: `GET /ai/jobs/{id}/review-context` НЕ нужен: фронт сам сравнивает `subject_version` с текущей карточкой. Метка «ИИ заполнил поле» в `card_meta` уже существует, при применении фронт использует тот же путь сохранения, что у ручного ответа.
- Решение по «заполнено не ИИ»: правило из п. 3.1 дизайна, по результату замера из Э0.

**Фронт (`features/ai` + правки `features/cards`).**

## Э4. Пачка

**Что видит пользователь.** В списке товаров «Заполнить с ИИ (N)» и подтверждение (админу штуки и минуты, владельцу диапазон ₴ и «хватит ли лимита»). Максимум пакета 30. ## 3. Что можно делать параллельно (разные сессии) и где конфликты

Правило слияния: Э0 → Э1 строго последовательно (ядро). После Э1 каждый этап в отдельной ветке от `master` после выкатки предыдущего ИИ-релиза, чтобы не ловить миграции и сгенерированные файлы.

| Пара | Можно ли | Как не пересечься |
|---|---|---|
| Э2 бэкенд и Э3 бэкенд | да | Э3 только читает `ai_jobs`/`ai_usage` и добавляет новые контроллеры/классы метрик; `AiJobs` и `AiAgent` не трогает |
| Э2 фронт (`features/ai` ядро, `features/cards`) и Э3 фронт | да после общего скелета из Э1 | Э3 делает свои экраны в своих папках (`ui/tasks`, `ui/metrics`); в чужие файлы (меню, `MetricsScreen`, виджеты) только отдельным коротким коммитом в конце |
| Э4 / Э5 / Э6 между собой | да | у каждого свои контроллер, сценарии `app`, своя фича `translation`/`supply`/`product`-панель; общее: `AiJobs` (не менять), `AiUnavailable` (не менять), `AiSettings` (каждый этап добавляет свои ключи в отдельный `SettingsContribution`-класс, не в один общий) |
| Что конфликтует всегда | | (1) `backend/src/test/resources/openapi/openapi.json` и `packages/core/src/api/generated.d.ts`: после слияния любой ветки пересоздавать (`-Dopenapi.update=true`, `npm run gen:api`), порядок слияния = порядок релизов; (2) номера миграций (таблица п. 1: не занимать чужой номер); (3) `i18n/messages*.properties` (добавлять в конец своим блоком `error.ai.<NAME>`); (4) `e2e/lib` и `docker-compose.e2e.yml` (`fake-ai.mjs` создаёт Э1, остальные только добавляют режимы в конец); (5) `frontend-admin/shell` и пункты меню (правит только Э3 и Э4: договориться, кто первый) |
| Параллельно с любым этапом | да | Ветка Новой почты (только ее номера миграций, после первой выкатки ИИ); SearXNG на сервере; замер `card_meta` |

Предлагаемая раскладка по сессиям: сессия A — Э0 затем Э1 (бэкенд ядро); после выкатки Э1: сессия B — Э2 фронт, сессия C — Э3 бэкенд и экраны метрик, сессия A — Э2 бэкенд (мало). После Э2/Э3: сессия A — Э4 бэкенд, B — Э4 фронт, C — Э5; Э6 стартует после Э4 бэкенда, чтобы не спорить за `AiJobs`/`ChatModel`.

6. Включение функции для админов только после недели личной проверки владельцем (выключатель в Настройках).

## 5. Открытые решения владельца, влияющие на сроки

Остаются те же 12 вопросов из `04-design-final.md` п. 14. Блокируют старт: №4 (кто владелец) и №11 (порядок миграций с Новой почтой) до Э1; №12 (замер `card_meta`) до Э2; №5 и №6 (массовое принятие, push админу) до Э4; №7 (поставка последней) подтверждена порядком выше.
