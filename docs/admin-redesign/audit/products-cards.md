# Аудит потерь: ТОВАРЫ И КАРТОЧКИ

Сравнение: старый код `frontend-admin/features/{product,cards,catalog,inventory}` против макетов `docs/admin-redesign/mockups/products-cards/` (варианты из README: список A; фильтры A на ПК / B на телефоне; цена-остаток A; редактор A; варианты A / фото B на телефоне; характеристики A; диалоги A; выбор категорий A на телефоне / B на ПК; карточки A, master-detail ≥1280; проверка A; оформление A).

Пути ниже даны от `frontend-admin/features/`. Пометки: «нет» = явно убрано в макете, «не показано» = в макете этого просто нет (возможно, не нарисовали). Оценка: КРИТИЧНО / ЗАМЕТНО / МЕЛОЧЬ.

Порядок: сначала критичное, потом заметное, потом мелочи.

## Критичное

### 1. Быстрая правка цены/остатка без защиты от гонки (expectedStock) и 409
- Где в старом: `product/ui/modal/use-product-save.tsx:207` — при сохранении уходит `expectedStock`; если остаток изменился (заказ, поставка), бэкенд отвечает 409 `STOCK_CONFLICT`, UI подтягивает свежий остаток (`refreshStock`) и показывает сообщение. Отдельного частичного PATCH цены/остатка в API нет (`product/api.ts`: `update` шлёт весь ProductWriteRequest).
- Что в новом макете: «цена-остаток A» — быстрая правка прямо в строке, но поведение при конфликте и при «остаток ушёл вниз» не показано.
- Критичность: КРИТИЧНО. Правка остатка в строке без expectedStock молча перезапишет остаток, изменившийся за это время (продажа, приход).
- Как вернуть: быстрая правка должна слать тот же `expectedStock`, а на 409 показывать в строке «остаток изменился: теперь N» с обновлением значения, а не перезаписью. Нужна явная заметка в ТЗ, что отдельного PATCH нет, а для быстрой правки придётся слать полную форму или добавлять эндпоинт.

### 2. Причины списания: набор в макете не совпадает с реальным
- Где в старом: `product/ui/modal/StockReasonDialog.tsx:42` и `inventory/model/writeoffs.ts:4` — причины DEFECT, INVENTORY, MISSORT, SOLD_OFFLINE, OTHER; при OTHER заметка обязательна (`needsNote`). Диалог обязателен, когда остаток уменьшают (`use-product-save.tsx:172` `askReasonIfLowered`).
- Что в новом макете: причины выдуманы по-другому (есть «Потеря», нет «Инвентаризация» и «Продан офлайн»); обязательность заметки для «Другое» не показана.
- Критичность: КРИТИЧНО. Причины попадают в журнал склада и отчётность; несовпадение с enum бэкенда даст 400 или кривую статистику.
- Как вернуть: взять список из `WRITEOFF_REASONS` один в один, оставить обязательную заметку для OTHER, убрать «Потерю» (или завести её на бэкенде осознанно).

### 3. Вкладки карточек: нет «Оформить», есть выдуманная очередь «В работе у ИИ»
- Где в старом: `cards/model/view.ts:16` — три вкладки по cardStatus: «Оформить» (черновики без карточки), «Проверить» (AI_FILLED), «Готово» (READY); `cards/model/screen.ts:12` `defaultTab` выбирает вкладку по счётчикам. Из «Оформить» запускается оформление и пакетный ИИ-мастер.
- Что в новом макете: «Оформить» как вкладки нет; вместо неё очередь «В работе у ИИ», которой в коде нет.
- Критичность: КРИТИЧНО. Пропадает вход в самый частый сценарий: взять неоформленные товары и отправить в мастер ИИ.
- Как вернуть: вернуть три вкладки с теми же именами и счётчиками; «в работе у ИИ» не придумывать (ответ ИИ вставляется вручную, фонового состояния нет).

### 4. Массовое «Показать» в обход PublishGate
- Где в старом: `product/ui/PublishGate.tsx` и `product/api.ts` `setActive` — публикация одного товара при 409 `CARD_NOT_READY` / `PRODUCT_NOT_PUBLISHABLE` открывает PublishGate (что не так + «Выложить без оформления» = `?force=1`).
- Что в новом макете: массовая панель «Показать» не показывает, что делать с товарами без готовой карточки; в диалоге публикации нет «Выложить без оформления».
- Критичность: КРИТИЧНО. Либо товары без карточки уйдут на витрину молча, либо массово не опубликуются без объяснения.
- Как вернуть: по каждому отказу собрать список «не опубликовано: причина», дать «Выложить без оформления» отдельным подтверждением.
