# Целевая архитектура бэкенда tg-shop-v2

**Статус: утверждено 29.10.2026.** Версия 1. Основа — карта кода master `7c7cf46` (486 классов, ~56 тыс. строк) и книги-скиллы (Clean Architecture,
Ousterhout, Fowler, Feathers, Nygard). Правила проверяет ArchUnit (см. `docs/ARCHITECTURE-CHECKS.md`) **на весь код без заморозки**: число нарушений = объём оставшейся работы, цель — ноль.

## 1. Что не так сейчас (коротко)

Одна и та же задача решена по-разному в разных местах — это и есть «костыли»:

| Задача | Сейчас — сколько способов |
|---|---|
| Где лежит код фичи | половина фич — свой пакет, половина размазана по `service/`, `web/`, `domain/`, `repository/` |
| Уведомления после сохранения | 3 способа: события+слушатель, `AfterCommit`+прямой вызов, прямой вызов Telegram из задачи |
| «Сделать после коммита» | утилита `AfterCommit` и ещё 6 ручных копий через `TransactionSynchronizationManager` |
| Журнал действий админа | то в контроллере, то в сервисе |
| Право «Финансы» | 3 способа (аннотация, ручная проверка в контроллере, `finance()` в каждом методе) |
| Время и часовой пояс | `Clock` в одних местах, `Instant.now()` в других, `Europe/Kyiv` зашит в 5 местах |
| Кэш | 4 механизма (Spring Cache, Caffeine в поле, `volatile`-мемо, `ConcurrentHashMap`) |
| Ошибки | исключения лежат в `web/`, ими пользуются сервисы; 404 места `BadRequestException`, код ошибки только у 72 |
| Ответы API | сервисы возвращают web-DTO (80 импортов `service → web`) |
| Настройки из `application.yml` | один `AppProperties` + 8 `@Value` в обход |
| Фоновые задачи | 21 `@Scheduled`, защита от двойного запуска — `AtomicBoolean` в двух, в остальных нет |
| Внешние вызовы | у каждого клиента свои таймауты, у Telegram и MinIO — никаких, ретраев нет нигде |
| Статус заказа | `setStatus` снаружи сущности в 7 местах; все 50 сущностей — только геттеры/сеттеры |
| Зависимости между пакетами | 198 циклов (catalog↔translation, gift↔order, preorder↔costing, adminauth↔security…) |

## 2. Целевая структура

### 2.1. Модули по бизнес-смыслу

`com.maxsolch.shop.<модуль>`. Каждый модуль — одна бизнес-способность; в нём всё, что к ней относится: API, сценарии, сущности,
хранение, интеграции. Технических корзин `service/`, `web/`, `domain/`, `repository/` на верхнем уровне не остаётся.

| Модуль | Что внутри (откуда переезжает) |
|---|---|
| `platform` | общая инфраструктура без бизнес-смысла: ошибки, время/пояс, события после коммита, HTTP-клиенты, задачи, конфиг, кэш, безопасность, i18n-сообщения, аудит, журнал «Бот и сайт», настройки из БД (`common`, `config`, `security`, `i18n`, `audit`, `journal`, `settings`, исключения из `web`) |
| `media` | файлы в MinIO, превью imgproxy, подписи ссылок |
| `site` | сброс кэша сайта (revalidate) |
| `translation` | переводы контента — **ничего не знает о товарах**: модули сами регистрируют свои переводимые поля (сейчас наоборот) |
| `catalog` | товары, варианты, фото, категории, бренды, характеристики, слаги, «Карточки», публичный каталог (`catalog`, часть `service`, `web`) |
| `inventory` | остатки, резерв под заказ, FIFO-партии, списания (`OrderStock`, `LotLedger`, `StockWriteoff*`) |
| `procurement` | поставщики, поставки, расходы, себестоимость, курс НБУ (`costing`, поставки из `preorder`) |
| `preorder` | очередь предзаказа, брони, подписки |
| `cart` | корзина |
| `promo` | промокоды, резервы, **один** генератор кода (сейчас 3 копии: подарки, отзывы, админка) |
| `order` | оформление, жизненный цикл, деньги заказа, правки, слияние, антибот, запросы отмены, чат заказа, админская доска |
| `returns` | возвраты, обмены, частичный выкуп, «едет назад» (из `OrderAdjustmentService`, разобран на шаге 1в: `returns.app` — `Returns`, `ReturnReceiving`, `Exchanges`, `ReturnCancellation`, `DefectWriteoffs`, `AdminReturns`) |
| `payment` | monobank, счета, чеки, возвраты денег |
| `delivery` | Нова пошта (справочники; дальше — ТТН из ветки `np-integration`) |
| `gift` | подарок за сумму, кейсы, реестр подарков |
| `review` | отзывы, модерация, бонус |
| `support` | обращения не по заказу, шаблоны ответов |
| `inbox` | экран «Внимание» |
| `customer` | покупатели, профиль, вход через Telegram/сайт, сессии, гео |
| `staff` | админы, 2FA, приглашения, команда, инциденты (`adminauth`, часть `web`) |
| `notification` | каналы доставки: бот покупателю, канал продавца, web push, рассылки (`tg`, `push`, `BroadcastService`) |
| `analytics` | события клиентов, воронка, метрики |
| `finance` | маржа, P&L, отчёты по деньгам (`MarginService`, «Финансы») |

### 2.2. Внутри каждого модуля — один и тот же шаблон

```
<модуль>/
  api/      контроллеры + DTO запросов/ответов + маппинг в DTO. Только разбор запроса → вызов сценария → DTO.
  app/      сценарии (use cases): один класс — одна группа действий одного актора. Транзакции, аудит,
            публикация событий, слушатели событий, фоновые задачи. Публичный API модуля для других модулей.
  domain/   сущности С ПОВЕДЕНИЕМ и инвариантами, value objects, чистые правила, события, порты
            (интерфейсы) к внешним системам.
  infra/    Spring Data репозитории, Jdbc-«Store»/«Queries» для отчётов, клиенты внешних систем (реализуют порты).
```

Правила зависимостей (проверяет ArchUnit):
- `api → app → domain`; `infra → domain`. `domain` не знает Spring Web, Jdbc, HTTP-клиентов, DTO.
- Другой модуль можно вызывать **только через его `app`** (и читать его `domain`-типы), никогда — его `api` или `infra`.
- Между модулями — **без циклов**. Обратное направление — только через события (модуль публикует, другой слушает)
  или через интерфейс, который объявляет вызывающий модуль (пример: `order` объявляет «расширение оформления заказа»,
  `gift` его реализует — так уходит цикл gift↔order).
- Направление модулей (сверху вниз, нижние не знают о верхних):
  `finance, analytics, inbox` → `review, support, gift` → `returns, payment, delivery` → `order` → `cart, promo` →
  `preorder` → `procurement` → `inventory` → `catalog` → `customer, staff` → `translation, media, site, notification` → `platform`.

### 2.3. Сознательные компромиссы (чтобы не было «архитектуры ради архитектуры»)

- **JPA-аннотации остаются на доменных сущностях.** Отдельная модель хранения удвоила бы 50 сущностей без пользы для
  магазина такого размера. Граница — «частичная»: сущность не знает про веб, DTO, HTTP, Spring-сервисы.
- **Интерфейс с одной реализацией — только для внешних систем** (monobank, Telegram, НП, MinIO, НБУ, push): это порт, за
  которым меняется поставщик и который подменяется в тестах. Для внутренних классов интерфейсов не заводим.
- Отчётные модули (`analytics`, `finance`, `inbox`) читают таблицы своим SQL — это нормальная read-модель, но **формулы денег
  только из `OrderMoney`**, а сами запросы лежат в `infra/*Queries`.
- Модули — пакеты в одном приложении, не микросервисы и не отдельные Maven-модули (это можно сделать позже, когда зависимости
  станут чистыми; сейчас — лишняя сборочная сложность).

## 3. Единые правила «как делаем» (одна задача — один способ)

| Задача | Единый способ | Чем проверяется |
|---|---|---|
| Статус заказа | `Order` — автомат состояний: `order.approve(...)`, `ship(ttn)`, `deliver()`, `reject(cause)`, `merge(...)`; сеттера статуса нет | ArchUnit: `setStatus` не существует |
| Деньги | `long` minor; формулы только в `OrderMoney` / методах `Order` | ArchUnit + golden |
| Ошибки | `platform.error`: `DomainException(ErrorCode, args)`; коды — enum в модуле; текст покупателю — через i18n по коду, админу — по-русски; HTTP-статус по типу ошибки в одном обработчике | ArchUnit: в `app`/`domain` нет `web`-исключений |
| Валидация | формат — Bean Validation на DTO в `api`; бизнес-правила — в `domain` | ревью |
| После коммита | только доменное событие + `@TransactionalEventListener(AFTER_COMMIT)`; `AfterCommit` и ручной `TransactionSynchronizationManager` удаляются | ArchUnit |
| Уведомления | модуль публикует событие → его `XxxNotifier` в `app` слушает и шлёт через порты `notification` (`CustomerBot`, `SellerChannel`, `PushSender`) | ArchUnit: Telegram/push только из `notification` и `*Notifier` |
| Аудит админа | в сценарии `app`, не в контроллере; кто действует — `CurrentActor` (вместо статического `SecurityUtil`) | ArchUnit: контроллеры не зовут аудит |
| Права | только аннотации: `@RequiredAdmin`, `@RequiredSuperAdmin`, новая `@RequiresFinance` | ArchUnit: нет ручных `require*` в контроллерах |
| Транзакции | `@Transactional` только на публичных методах `app`; в `api` — нет | ArchUnit |
| Блокировки | только в БД (`SELECT … FOR UPDATE`); замки в памяти (`ConcurrentHashMap`, `synchronized`) уходят — иначе второй экземпляр бэкенда их не видит | ArchUnit |
| Время | бин `Clock` + `ShopZone` (часовой пояс из конфига); `Instant.now()`/`ZoneId.of` вне `platform` запрещены | ArchUnit |
| Конфиг | `@ConfigurationProperties` с `@Validated` на модуль; `@Value` запрещён | ArchUnit |
| Кэш | только Spring Cache (Caffeine) с именованными кэшами и TTL; самодельные мемо удаляются | ArchUnit |
| Фоновые задачи | `app/*Jobs` + ShedLock (замок в БД, одна новая таблица) — задача не запустится дважды | ArchUnit: `@Scheduled` только в `*Jobs` с `@SchedulerLock` |
| Внешние HTTP | порт в `domain`, клиент в `infra` через общий `platform.http`: таймауты обязательны, ретраи — только идемпотентных вызовов, ограниченные; Telegram и MinIO получают таймауты | ArchUnit + тест конфигурации |
| Зависимости бинов | только конструктор; `@Autowired(required=false)`, сеттеры, поля, `@Lazy` — нет | ArchUnit |
| Ответы API | `app` возвращает доменные объекты/read-модели, DTO собирается в `api` | ArchUnit: `app`/`domain` не импортируют `api` |
| Доступ к данным | Spring Data по умолчанию; `JdbcTemplate`/native SQL — только в `infra/*Store`/`*Queries` | ArchUnit |
| Размер | класс ≤ 500 строк, метод ≤ ~60; без исключений в конце | `ClassSizeTest` без списка |
| Тесты | домен — быстрые юниты без Spring; сценарии — с фейками портов; транзакции/локи/события — IT на MySQL; DTO — golden; тексты — snapshot | CI |

## 4. Заказ — как будет выглядеть ядро

- `order/domain/Order` — агрегат: позиции меняются только через его методы (`addItem`, `changeQuantity`, `removeItem`,
  `applyDiscount`), статус — через переходы с проверкой из таблицы переходов, деньги — `order.money()` (`OrderMoney`).
  Каждый переход возвращает/регистрирует доменное событие.
- `order/app`: `Checkout` (оформление), `OrderLifecycle` (одобрить/отправить/доставить/отклонить/истечение срока),
  `CancelRequests`, `OrderEditing`, `OrderPayments` (ручные оплаты), `OrderMerge`, `CustomerOrders` и `AdminOrderBoard` (чтение).
  Вместо `OrderService` (1629 строк) и `OrderAdjustmentService` (1222) — 8–10 классов по 150–350 строк.
- `returns/app`: `Returns`, `Exchanges`, `PartialPickup` — каждое действие мастера возврата отдельно.
- Склад — только через `inventory/app/Stock` (резерв, возврат, партии), деньги — через `payment/app`.

## 5. Порядок переезда (помодульно, каждый шаг — в master после CI)

Каждый шаг: характеризующие тесты → перенос без изменения поведения → нарушения ArchUnit по модулю = 0 → CI → master.
API (URL и JSON), схема БД и поведение не меняются; защищают golden-JSON, snapshot-тексты, IT и e2e админки.

| Шаг | Что | Примерный объём |
|---|---|---|
| 0 | `platform`: ошибки с кодами, `Clock`/`ShopZone`, события после коммита, `platform.http`, ShedLock, `@ConfigurationProperties`, `CurrentActor`; новые правила ArchUnit с подсчётом нарушений по модулям | основа для всего |
| 1 | `order` + `returns` + `cart` + `promo` (самый больной; уже подготовлен №1–6) | самый большой |
| 2 | `payment`, `delivery` | средний |
| 3 | `inventory`, `procurement`, `preorder` (рвём цикл preorder↔costing) | средний |
| 4 | `catalog`, `translation` (переворот зависимости), `media`, `site` | большой |
| 5 | `gift`, `review`, `support`, `inbox` | средний |
| 6 | `customer`, `staff`, `notification` (+ рассылки) | средний |
| 7 | `analytics`, `finance` | небольшой (уже чистые) |
| 8 | финал: удалить старые пакеты и списки заморозки, `open-in-view: false`, лимит 500 строк без исключений | проверка |
| 9 | фронты (сайт, Mini App, админка, shared) — отдельный документ целевой структуры по тому же принципу | отдельный этап |
