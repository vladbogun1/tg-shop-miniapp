# UI-FIXES — ветка `улучшение`

Второй заход по дефектам (после `AUDIT-FIXES.md`). Список составлен по разбору
8 скриншотов с телефона + замечаниям владельца. Сверяться по этому файлу, пока
не закрыто всё; `[x]` ставится только после проверки в браузере локально.

Ограничения те же, что и в прошлый раз: зависимости не обновляем, локаль русская,
тема — нео-брутализм.

## 1. Промокод: валидация и резерв ещё в корзине

Сейчас код вводится в корзине, никак не проверяется, а «инвалид» прилетает на
последнем шаге оформления, где его уже не убрать. Финальный шаг НЕ трогаем.

- [x] Корзина: проверка кода на сервере с дебаунсом (`components/cart/PromoField.tsx`),
      зелёная рамка и сумма скидки / красная рамка и причина.
- [x] Код можно очистить одной кнопкой; резерв при этом сразу возвращается.
- [x] Итоги в корзине и сумма на кнопке «Оформить» считаются со скидкой;
      оформление использует ту же проверку, так что экраны не расходятся в цене.
- [x] Бэкенд: `PromoService` + таблица `promo_reservations` (V15) — лимитированный
      код держится за покупателем 30 минут, освобождается по истечении, при очистке
      кода и при создании заказа. Безлимитные коды не резервируются.
- [x] Свободных применений = `max_uses - uses_count - чужие живые резервы`;
      создание заказа считает так же, поэтому чужой резерв не уводят.
- [x] Тесты: `PromoServiceTest` (8 случаев), вся сборка — 102 теста зелёные.

## 4. Чат: скорость фото, «Подключение…», выход назад

- [x] `/api/media` отдавал ОРИГИНАЛ. Добавлен параметр `w` (белый список размеров) —
      бэкенд отдаёт уменьшенный вариант через внутренний imgproxy
      (`MediaThumbnailer`), приватность ссылки не меняется. Замер на реальном
      вложении: 102 КБ → 8 КБ для пузыря; на фото с телефона разница в разы больше.
- [x] `MediaSigner` выдавал новый `exp` на каждый ответ, из-за чего ссылка каждый раз
      была новой и браузерный кэш не работал. Срок округляется до получасового окна.
- [x] В пузыре запрашивается превью (480), полный размер — только в просмотрщике.
- [x] `proxy_buffering off` для `/api/media` в обоих gateway.
- [x] **Найдена причина «не с первого раза прогрузило чат»:** запросы `/api/me/**`
      стартовали до того, как initData обменивался на JWT, ловили 403, и экран
      оставался с ошибкой. Все такие запросы теперь ждут токен (`lib/auth.ts`),
      «ждём токен» показывается скелетоном, а не пустым состоянием.
      В консоли после правки — ноль 403.
- [x] Выход назад из чата проверен локально; главная причина залипания (декодирование
      многомегабайтного фото в главном потоке) убрана вместе с размером.
- [x] Аналитика кликов: `lib/analytics.ts` — буфер в localStorage, отправка пачкой
      раз в 15 с и при сворачивании/закрытии (`keepalive`), приём
      `POST /api/me/analytics` с лимитом 20 пачек/мин на IP, таблица `client_events`
      (V16), чистка старше 30 дней. Значения полей не пишутся — только что нажали.

## 6. Неверный промокод больше не запирает оформление

Найдено владельцем после выкатки `v2.7.0-rc1`: корзина честно писала «Промокод не
найден», но «Оформить» всё равно уводил дальше, а на последнем шаге прилетало
`invalid promo code` — и выйти было некуда, потому что поле осталось в корзине.

- [x] Оформление отправляет промокод, ТОЛЬКО если сервер подтвердил его валидность.
      На кнопке в этом случае и так стоит сумма без скидки, так что заказ создаётся
      ровно на ту сумму, которую человек видел.
- [x] Гонка (код был валиден в корзине, но последнее применение забрали, пока человек
      шёл по шагам) больше не тупик: бэкенд помечает отказ кодом `PROMO_REJECTED`,
      приложение убирает промокод из корзины, пересчитывает итог и просит нажать ещё
      раз. Проверено: сообщение «Промокод уже разобрали. Промокод убран — оформите
      заказ ещё раз», повторное нажатие создаёт заказ.
- [x] `invalid promo code` / `promo code usage limit reached` заменены на русские
      тексты; приложения теперь смотрят на `code`, а не на текст (`ApiError.code`).
- [x] **Попутно найдено:** `Idempotency-Key` не был в `Access-Control-Allow-Headers`,
      поэтому при разных origin (локальный дев-сервер, туннель) preflight резал
      `POST /api/orders` — заказ не уходил вообще. На проде один origin, preflight
      не отправляется, поэтому дефект там не проявлялся.
- [x] Локальный стенд больше не может написать в настоящий Telegram: в
      `docker-compose.dev.yml` пустые `BOT_TOKEN`/`NOTIFY_CHAT_ID`, иначе тестовый
      заказ ушёл бы карточкой в реальный канал и личкой покупателю.

## Что проверить руками на телефоне

Стенд не эмулирует клиент Telegram, поэтому на устройстве стоит посмотреть:

1. Клавиатура: таб-бар и блок «Итого» должны уезжать при вводе промокода
   (логика на `visualViewport`, в браузере проверена подменой высоты).
2. Оформление на маленьком экране: шапка, карта и кнопка «Выбрать это отделение».
3. Чат: скорость открытия фото и то, что «Подключение…» сменяется на «В сети».
