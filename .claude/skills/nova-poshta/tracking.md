# Отслеживание ТТН и коды статусов

## Старый API — `TrackingDocument.getStatusDocuments` (рекомендуем для этапа 1)

> Песочницы нет; поля — по `shopanaio/carrier-api` (`src/types/tracking.ts`) и практике. Официальная страница за Cloudflare.

```json
{
  "apiKey": "<UA_BUSINESS_KEY>",
  "modelName": "TrackingDocument",
  "calledMethod": "getStatusDocuments",
  "methodProperties": {
    "Documents": [
      {"DocumentNumber": "20450000000000", "Phone": "380XXXXXXXXX"},
      {"DocumentNumber": "20450000000001", "Phone": "380XXXXXXXXX"}
    ]
  }
}
```

- **До 100 ТТН** за запрос. `modelName` встречается и как `TrackingDocumentGeneral`.
- **`Phone`** — телефон отправителя или получателя этой ТТН. Без него (или с чужим) приходит урезанный ответ: статус и даты есть,
  но нет ПІБ/телефонов/адреса (`RecipientFullName`, `PhoneRecipient`, `RecipientAddress`, суммы к оплате и т.п.).
  Для ТТН, созданных нашим ключом (наш контрагент — отправитель), по практике полные данные приходят и без телефона; всё равно
  передавайте телефон получателя из заказа — это бесплатно и закрывает случай ТТН, созданных вручную/в приложении.
- Ключ — наш бизнес-ключ (без ключа метод тоже отвечает, но с лимитами — не полагаться).
- Ответ: `data[]` по одному объекту на ТТН (порядок = порядок запроса).

Полезные поля ответа:

| Поле | Смысл |
|---|---|
| `Number`, `StatusCode` (строка!), `Status` | номер, код (см. таблицу), текст для людей |
| `ScheduledDeliveryDate`, `ActualDeliveryDate`, `RecipientDateTime` | план, факт прибытия, факт получения |
| `WarehouseRecipient`, `WarehouseRecipientRef`, `WarehouseRecipientNumber`, `CityRecipient`, `RefCityRecipient` | куда пришло (сравнить с заказом) |
| `DateFirstDayStorage`, `DatePayedKeeping`, `StorageAmount`, `DaysStorageCargo` | когда начнётся платное хранение — для напоминаний |
| `UndeliveryReasons`, `UndeliveryReasonsSubtypeDescription`, `UndeliveryReasonsDate` | причины невручения/отказа |
| `LastCreatedOnTheBasisNumber`, `…DocumentType` (`Return`, `Redirecting`…), `OwnerDocumentNumber` | ТТН возврата/переадресации |
| `RedeliverySum`, `RedeliveryNum`, `LastTransactionStatusGM`, `LastAmountTransferGM` | наложка: сумма, номер переказа, статус выплаты |
| `AfterpaymentOnGoodsCost` | «Контроль оплати» |
| `DocumentCost`, `AmountToPay`, `AmountPaid`, `PayerType`, `PaymentMethod` | стоимость доставки и кто платит |
| `PossibilityCreateReturn`, `PossibilityCreateRedirecting`, `PossibilityTermExtension` | доступные действия |

## Новый REST

Схемы: [reference/portal/methods__methods__shipments__tracking-shipment.md](reference/portal/methods__methods__shipments__tracking-shipment.md).

- `GET /shipments/tracking?numbers[]=…&withUndeliveryReason=true&withCreatedOnTheBasis=true` (**FullTracking**) →
  `items[]{currentStatus, detailsTracking[], historyOnlineTracking[], parcels[], alternativeNumbersGW[], undeliveryReasons[], createdOnTheBasis[]}`.
- `GET /shipments/tracking/history?numbers[]=…&extended=1` (**BasicTracking**) → `items[]{id, number, scheduled_delivery_date, history_tracking[]{code, code_name, country_code, settlement, date}, related_numbers[]}`.
  Тот же формат, что в вебхуке.
- Телефон не нужен, но видны только **свои** ТТН (созданные этим клиентом / где он отправитель-получатель). ТТН из чужого кабинета: 404.
- Песочница ([40-tracking-full.json](reference/sandbox-examples/40-tracking-full.json)): `currentStatus` пришёл **объектом**
  (в OpenAPI — массив), `statusCode` — число, `code` в истории — строка; размеры в `parcels` — **см/кг** (создавали в мм/г).
  Неизвестный номер: FullTracking → 404 `Shipments not found`, BasicTracking → 404 `not_found`.
- Логику строить на числовых `code`/`statusCode`, не на `event`/`status`/`code_name` (меняются, бывают одинаковые).

### Коды `statusCode` нового API (UA-значимые выделены)

**1** готово до відправки · **2** видалено · **4** прийнято до відправки · **5** відправлено з відділення відправника ·
**6** прибуло в місто отримувача · **7** прибуло у відділення · **8** прибуло у поштомат · **9** закрито (отримано) ·
**10** закрито, переказ відправлено · **11** закрито, переказ отримано · 13/16 транзитний сортцентр · 17/19 не використовуються ·
30/31 митний термінал · 70 додано до маніфесту (тільки вебхук) · 80/81 авіа · **99** доставка в поштомат неможлива ·
**101** у кур'єра на доставку · **102** повернення (відправник замовив) · **103** відмова від отримання · **104** переадресація ·
**105** утилізація · **106** отримано і створено зворотну доставку документів · 107 у пункті видачі (тільки вебхук) ·
**110** передано на тимчасове зберігання · **111** невдала спроба доставки · **112** дату доставки перенесено ·
**113** термін зберігання в поштоматі сплив · 114–135, 197–199 митниця · 138 затримка через невірні дані отримувача ·
**141/144** термін зберігання сплив · **149** на зберіганні · **155** передано на утилізацію · 999 невизначено.

Коды 1–12 и 101–112 совпадают по смыслу со старым API (3 «не знайдено» в новом заменён на 404).

`event` в `detailsTracking` (полный список — в файле схемы): ключевые для UA — `CreateID`, `Deleted`, `ArrivalSenderWarehouse`,
`DepartureSenderWarehouse`, `InCityRecipient`, `ArrivalRecipientWarehouse`, `ArrivalRecipientPostomat`, `ReceivedWarehouse`,
`ReceivedDoors`, `MoneyTransfer`, `UndeliveryReasonsClient`, `OrderCargoReturn`, `EWCargoAutoReturnRecipient`, `ShelfLifeHasExpired`.
`eventStatus`: `passed` / `now` / `future` (пришло в нижнем регистре, в доке — с заглавной).

## Карта → статусы заказа (наша рекомендация)

`OrderStatus`: `NEW → APPROVED → SHIPPED → DELIVERED`, `REJECTED`.

| Код NP | Действие в магазине |
|---|---|
| 1, 12 | ничего (ТТН создана, посылку ещё не сдали). Если висит >2 суток после «отправлено» — напомнить админу |
| 4, 41, 5, 6, 101 (новый: 4, 5, 6, 13, 16, 101) | если заказ `APPROVED` — перевести в `SHIPPED` (посылку сдали); иначе ничего |
| **7, 8** (новый: 7, 8, 107) | уведомить покупателя «прибыло в отделение/поштомат №…», запомнить `DateFirstDayStorage` для напоминания перед платным хранением |
| **9, 10, 11** | `DELIVERED` (финал; 10/11 — дополнительно отметить выплату наложки) |
| **103** | уведомить админа «отказ получателя»; заказ не закрывать до возврата |
| **102, 104, 105, 106** (новый: + 113, 141, 144, 155) | возврат/переадресация/утилизация: уведомить админа; по `LastCreatedOnTheBasisNumber` начать трекать ТТН возврата; заказ → `REJECTED` (или отдельный «возврат», если появится) после получения возврата |
| 111, 112, 99, 110, 149, 138 | инфо в журнал заказа, при необходимости — уведомление |
| 2 | ТТН удалена — снять `tracking_number`, уведомить админа |
| 3 / 404 | номер не найден — ошибка ввода ТТН, уведомить админа |

Финальные (больше не опрашивать): 2, 3, 9, 10*, 11, 102/103 после получения возврата, 105, 106. (*10 — опрашивать до 11, если важна выплата.)

Требует телефона (старый API, для чужих ТТН): ПІБ и телефоны сторон, адрес, суммы к оплате. Сам `StatusCode`, даты и отделение
приходят и без телефона. Набор «закрытых» полей точно не документирован — проверить на первой боевой ТТН и зафиксировать здесь.
